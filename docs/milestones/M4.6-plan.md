# M4.6 — Users, roles and the account surface

> ## DECISIONS TAKEN SINCE THIS PLAN WAS WRITTEN
>
> This plan was drafted while the questions below were still open, so it may present two branches or defer to "an owner decision". **It no longer does.** The rulings are binding; where the plan below offers a choice this section has already made, follow this section. Full reasoning and evidence are in [`ROADMAP-to-M5.md`](ROADMAP-to-M5.md#decisions-taken).
>
> **Decision 170 — Should push subscribe/unsubscribe be gated behind a non-PIN session, and should SetPinRequest require the current password?**  
> Gate both. `POST /api/push/subscribe` and `DELETE /api/push/subscription` move behind the same `credentialed_user` dependency as passkey registration, and `SetPinRequest` gains a required `current_password` verified exactly the way `change_password` verifies it (auth.py:216-218), in the same UPDATE that clears `pin_failed_count`/`pin_locked_until`. The rule to write down is: a PIN session reaches the product surfaces and nothing that changes how the account is reached later — and setting the PIN itself is such a change, so it costs the account's own password whatever session you are in.
>

**M4.6 is not in the original §12 build order.** The row was added to §12's table this week,
uncommitted, together with the §3.1/§6.2/§6.5/§6.6 amendments that owner decisions **164**, **165**

screen and closes the account rules behind it, so the household can make a second member and a
PIN-switched session cannot escalate into a permanent credential.

## 1. Why these thirty-three findings are one milestone

Every one of them is a write or a gate on `app_user`, `auth_session` or `webauthn_credential`, and
every one passes through five files: `api/setup.py`, `api/auth.py`, `api/passkeys.py`,
`core/auth.py` and `api/deps.py`. The review's coupling map states the anti-seam plainly: there is no
seam between the account set and the auth-hardening set. Three sequencing facts turn that from an
observation into a scoping rule.

**The screen is not a separable UI task.** `AdminTabs.svelte:14` parks the Users tab at `href: null`,
so the tab renders as a dead label. Turning it into a link needs `as10`'s lifecycle routes (nothing
in the shipped code ever *writes* `role`, `is_active` or a replacement `password_hash` —
`app_user.is_active` is read in six places and written in none), `cs-09`'s two-role table, and
`sec-01`'s credentialed-user gate. Without them it ships a screen that mints accounts nobody can
reset, on a table that still admits a role §3.1 has deleted.

**Two edits must be atomic or the build is red for everyone.**
`backend/tests/test_spec_coverage.py:113-116` asserts `covered == set(MILESTONES)`. Adding `"M4.6"`
to `MILESTONES` (`test_spec_coverage.py:31`) without at least one M4.6 row in `spec_coverage.toml`
fails `test_every_milestone_is_represented` for every developer on the branch, on a test that has
nothing to do with the change being made. One commit, both edits.

**The wizard cleanup follows the screen, never precedes it.** `cs-09` says it in one line and it is
the ordering rule of the whole milestone: delete `setup/+page.svelte`'s member step before
`/admin/users` exists and the install has no account-minting path at all.

The milestone also lands the house transaction/advisory-lock idiom in `api/deps.py`
(`dd-api-routes-write-without-transactions`), because it owns that file and needs the idiom for
`as04`'s first-boot race. M4.10, M4.11 and M4.12 then apply that one idiom at their own seams instead
of inventing three.

### The PIN-switch escalation chain

**8. A PIN-switched session mints permanent credentials on the account it switched into.**
`[sec-01-pin-session-can-register-passkeys-and-reset-pin]` — **critical, and the reason this
milestone is not just a screen.** A session from `POST /api/auth/switch` carries
`auth_method='pin'` (`api/auth.py:163`) and is a full `ActiveUser`: `api/deps.py:36-45` checks only
`must_change_password`, and `auth_method` (`core/auth.py:160`) is consulted nowhere in `deps.py`.
Reproduced over HTTP from a PIN session: `POST /api/auth/passkey/register/options` and
`/register` (`api/passkeys.py:42-49`, both `ActiveUser`) are 200; `POST /api/auth/pin`
(`api/auth.py:230-237`) is 200 with neither the current PIN nor the password, replacing the victim's
PIN; `DELETE /api/auth/passkey/credentials/{id}` (`api/passkeys.py:68-69`) is 200; `POST
/api/push/subscribe` (`api/push.py:132-133`) is 201. Against the admin account the chain defeats the
24 h re-prompt: the PIN session itself is refused on `/api/admin/*` because `core/auth.py:189` stamps
`admin_verified_at` only `CASE WHEN $5 <> 'pin'`, but the passkey it just registered logs in with
`auth_method='passkey'` (`api/passkeys.py:96-97`), which *is* stamped. The admin's later password
change revokes sessions (`core/auth.py:236-245`) and leaves the attacker's `webauthn_credential` row
in place. **Should:** §3.2 makes the password the always-available account credential and the PIN a
convenience; credential management requires the credential.

**9. An OTP-locked account reaches five routes the code says it cannot.**
`[spec-05-locked-account-row-tests-a-flag-while-four-routes-stay-open]` `api/auth.py:210` calls
`/password` "The one route reachable while `must_change_password` is set (§3.1)" and
`core/auth.py:7-9` says the auth layer refuses "every route but the change-password one".
`api/deps.py:36-45` is the only place the lock lives, and five routes plus `/me` take `CurrentUser`
instead of `ActiveUser`: `pin_switch` (`api/auth.py:143-144`), `set_pin` (`:231`, with the rule
re-implemented by hand at `:232-233`), `set_preferences` (`:241-242`), `switchable` (`:257`),
`credentials` (`api/passkeys.py:63-64`) and `complete_onboarding` (`api/setup.py:146-147`). Measured
with a locked session: all 200, and after `POST /api/auth/switch` the locked holder is inside another
member's fully active session. Coverage row `platform-forced-first-login-change` says "every other
authenticated route is refused" and its named tests assert a flag in the database; the HTTP test that
does exercise the lock (`backend/tests/test_api_gating.py:219-233`) checks two routes and is not named
in the row. **Owner call required on one of the six** — see §4, step 8.

**10. The PIN lockout disables itself at 42 failures.**
`[as-01-pin-lockout-interval-overflow-disables-the-lockout]` `core/auth.py:139-141` computes
`$3::interval * power(2, pin_failed_count + 1 - $2)` and applies `least(..., 1 h)` *afterwards*.
Postgres evaluates the product first; `least(interval '1 minute' * power(2, n), interval '1 hour')`
succeeds through n=37 and raises `DatetimeFieldOverflowError` from n=38 — i.e. from
`pin_failed_count = 42`. The route then answers 500 "database error", the counter and
`pin_locked_until` are left unchanged, and every subsequent wrong guess repeats it. The comment at
`:128-132` calls the lockout "the actual defence for a 10^4 keyspace (the hash is not)"; from 42 on
there is none. **Should:** cap the exponent before multiplying.

**11. A passkey assertion with the UV flag clear stamps the admin clock like a typed password.**
`[sec-06-passkey-user-verification-not-required-yet-counts-as-admin-verification]`
`core/webauthn.py:131` and `:215` both request `UserVerificationRequirement.PREFERRED`;
`verify_authentication_response` at `:255-262` is called without `require_user_verification`, and
`:268-273` discards `verified.user_verified`. §3.2's stated passkey is Face ID / Touch ID / Android
biometrics, so a presence-only tap on a roaming key satisfies the 24 h admin re-prompt.

**12. The documented sign_count replay guard is inert for synced passkeys.**
`[as-09-sign-count-replay-guard-is-inert-for-zero-counter-passkeys]` py_webauthn skips the counter
comparison when both counters are 0, which is what synced iCloud/Google passkeys — §3.2's target —
report; `core/webauthn.py:15-17` and the comment at `:263-266` claim otherwise, and
`test_a_replayed_assertion_is_refused` covers hardware-counter keys only. The `UPDATE` at
`:269-272` is unconditional on the stored counter. Not a vulnerability (the challenge is single-use,
`_consume` at `:64-71` deletes it), but the claimed property is narrower than the code and the tests
state.

### Admin re-auth

**13. The 24 h re-prompt has no clearing route and its only affordance loops.**
`[sec-05-admin-reauth-has-no-route-and-the-shell-link-loops]` `admin_verified_at` is written only at
INSERT (`core/auth.py:189`); there is no `UPDATE` anywhere in `backend/spielplan/` or the migrations.
Once the stamp is stale all twelve admin routes 401 with `X-Spielplan-Reauth` (`api/deps.py:54-60`)
and no authenticated route clears it. The only clearing path is `POST /auth/login`, which creates a
second live session while the stale row stays valid, and the shell's only affordance is
`<a class="btn-primary" href="/login">Sign in again</a>` (`+layout.svelte:107`) while `guard()`
(`:58`) sends any live session on `/login` straight back to `/`. `ApiError.needsAdminReauth`
(`frontend/src/lib/api.js:24-25`) is parsed and consumed nowhere, so a long-open tab shows raw 401s.
The shipped test documents the workaround as the behaviour
(`backend/tests/test_api_gating.py:133-135`: "Signing in again with the password is what clears it —
that is the whole re-prompt").
*Correction to the finding:* it cites `test_api_gating.py:372-374`; the file is 266 lines and the
assertion is at `:133-135`.

**14. `ADMIN_REAUTH_HOURS` accepts 0 and negatives and locks the admin out permanently.**
`[dd24-reauth-hours-zero-or-negative-locks-admin-out-permanently]` `core/config.py:39` declares
`admin_reauth_hours: int = 24` with no bounds and no validator, and `core/auth.py:177` compares
`now - self.admin_verified_at > timedelta(hours=settings().admin_reauth_hours)` — true milliseconds
after the INSERT when the value is 0. An operator who reads 0 as "off" makes the admin surface
permanently unreachable, showing the same "more than 24 hours old" banner in a loop.

**15. `SESSION_DAYS` is unvalidated, and the blast radius is everyone.**
`[cs-45-session-days-unvalidated]` `core/config.py:38` — `session_days: int = 90`, no validator. With
`SESSION_DAYS=0` the admin-creation response carries `Max-Age=0`, `POST /api/auth/login` returns 200
with a fresh cookie, and `GET /api/auth/me` returns 401. Three consumers trust it:
`core/auth.py:184` (row expiry), `core/auth.py:213-217` (the slide), `api/auth.py:51` and
`api/setup.py:86` (the cookie). Fixing only `ADMIN_REAUTH_HOURS` leaves this open, so both are one
repair.

### Session hygiene

**16. The 90-day window slides in the database and never in the cookie.**
`[as-02-session-cookie-max-age-never-slides]` `set_session_cookie` (`api/auth.py:44-56`) writes
`Max-Age = session_days * 24 * 3600` exactly once, at login (`:133`), PIN switch (`:164`), passkey
login (`api/passkeys.py:99`) and first admin (`api/setup.py:83-91`, a duplicated block).
`load_session` (`core/auth.py:212-218`) slides `expires_at` on every request, and no response after
login carries `Set-Cookie`. So the browser discards the cookie 90 days after the last explicit login
even under daily use, while the row it points at stays valid and orphaned for up to another 90 days.
The lapsed 401 (`api/deps.py:29`) also sends no clearing `Set-Cookie`. Coverage row
`platform-session-cookie-contract` claims the sliding behaviour and is green on database-only tests.

**17. Every authenticated request UPDATEs the session row.**
`[as14-session-row-updated-on-every-request]` `core/auth.py:213-218` is unconditional, so each page's
fan-out is N serialised row updates plus N rewrites of `auth_session_expiry`
(`0002_users.sql:61`). Not a correctness bug alone — but it is the same statement the cookie slide
must be driven from, which is why it and finding 16 are one repair.

**18. Re-login leaves the replaced session alive.**
`[dd24-relogin-never-revokes-the-replaced-session]` `api/auth.py:130-133` and
`api/passkeys.py:96-99` create a session and never destroy the sid the incoming cookie names.
`pin_switch` already does exactly that, with a comment explaining why
(`api/auth.py:161-163`: "The device is handed over, so the session it was holding does not travel
with it"). The worker's prune (`worker.py:51-56`) deletes expired rows only. With the re-auth loop
of finding 13 the admin creates one orphan 90-day credential per day.

### The write path

**19. No route in `api/` opens a transaction.**
`[dd-api-routes-write-without-transactions]` `grep -rn 'transaction()' backend/spielplan/api/*.py`
returns nothing, against 29 hits in the domain packages. The DB dependency (`api/deps.py:14-19`) is
a bare pooled connection, so every statement autocommits. `api/setup.py:70-84` issues the `app_user`
INSERT, the `setup_step` INSERT and `create_session` as three independent statements; a failure after
the first leaves an admin row whose password was typed once into a form that errored, and
`GET /api/setup/state` then reports `required=False`.

**20. Two concurrent first-boot admins both succeed, and a duplicate name is a 500.**
`[as04-first-boot-admin-race-and-duplicate-name-500]` `api/setup.py:67-77` does
`SELECT count(*) ... WHERE role='admin'` and then INSERTs, with no transaction and no lock. With a
warmed pool, `asyncio.gather` of two submits with different names returned 201 and 201 and
`app_user` held two admins. With the same name the loser's `app_user_name_key`
(`0002_users.sql:26`) violation reaches `app.py:114-117`'s generic `asyncpg.PostgresError` handler as
500 "database error" instead of 409; `create_member` has the same shape, so a double-tapped form
gives 201 + 500. The route's own docstring (`:65-66`) says it must only be callable while no admin
exists because it is otherwise "a privilege-escalation endpoint reachable by anyone who can see the
setup page" — and decision 166 names the same fact: an install that reaches zero admins lets an
anonymous caller mint one, which is why the last-admin floor is a security requirement.

### Login hardening

**21. Password login is unthrottled and every attempt costs 64 MiB on the event loop.**
`[sec-02-password-login-unthrottled-argon2-memory-dos]` `api/auth.py:117-119` verifies argon2
unconditionally (correctly, for timing parity against `ABSENT_ACCOUNT_HASH`, `core/auth.py:86`) with
argon2-cffi defaults measured at t=3, m=65536 KiB, p=4 (~30-34 ms). There is no per-account counter,
no per-IP limit, no concurrency cap and no `max_length` (`api/auth.py:20-23`). Only the PIN path has
a lockout. Every argon2 call is synchronous inside `async def` — `api/auth.py:117`, `:127`, `:154`,
`:217`, `:224`, `:235` and `api/setup.py:76`, `:131` — so eight concurrent wrong-password logins took
an unrelated `GET /api/health` from 38 ms to 223 ms. §2 puts the same origin behind Tailscale, which
bypasses Cloudflare rate limiting, on a 4 vCPU box.

**22. Malformed passkey payloads escape as 500s on an anonymous route.**
`[sec-04-malformed-passkey-payload-500s-on-anonymous-route]` `core/webauthn.py:32-35` imports only
`InvalidRegistrationResponse` and `InvalidAuthenticationResponse`; py_webauthn 3.0.0 raises sibling
`WebAuthnException` subclasses (`InvalidJSONStructure`, `InvalidCBORData`,
`InvalidAuthenticatorDataStructure`, `InvalidBackupFlags`) for structural problems, and `credential:
dict` is unvalidated client input on both routes (`api/passkeys.py:25-28`, `:36-39`). Reproduced:
`register` with `credential={}` raises out of the app for any signed-in member; `login` with a
registered credential id — which every member can read from their own account page — and
`response={}` does the same. The challenge is consumed before the failure, so the user must start
over with an unexplained error. A NUL byte in a login name reaches Postgres and answers 500.

**23. Names are not normalised, PIN digits are Unicode, and login bodies are unbounded.**
`[as-11-account-names-are-not-normalised-and-pin-digits-are-unicode]` `api/setup.py:27` and `:38`
check length only; the unique index is on `lower(name)` with no trim; login matches
`lower(name) = lower($1)` exactly. Creating `' Tom '` returns 201, login as `'Tom'` returns 401,
and a second account `'Tom'` can then be created beside it — two identical-looking chips in the
switch list. `SetPinRequest`'s `r"^\d+$"` (`api/auth.py:37`) is Unicode-aware in pydantic's regex
engine: `١٢٣٤` and `１２３４` were accepted. `PinSwitchRequest` (`:26-28`) carries the length bounds
but **no** pattern at all, so the two ends of the same PIN disagree about what a PIN is.

**24. Anonymous routes write rows without bound and disclose the install state.**
`[sec-14-anonymous-routes-write-rows-and-disclose-install-state]` `POST
/api/auth/passkey/login/options` (`api/passkeys.py:78-81`) is anonymous and inserts a challenge row
per call (`core/webauthn.py:75-79`); `_issue` never deletes expired rows inline and there is no cap —
60 anonymous calls left 60 rows, pruned only by the hourly worker (`worker.py:59-65`).
`GET /api/setup/state` (`api/setup.py:42-60`) is anonymous and returns `has_admin`, `member_count`,
the active bundle version and `imported_at` and which wizard steps are done, where the login page
needs only `required`.

### The frontend account surface

**25. The account chip claims a passkey and a PIN nobody has.**

**A new migration is genuinely needed: `backend/migrations/0016_users.sql`.** `0015_seed.sql` is the
highest applied file, so 0016 is the next free number. Applied migrations are sha256-checksummed and
a mismatch is a hard startup error — **never edit 0002_users.sql**, which is where `role`'s CHECK,
`app_user_name_key` and `auth_session` live.

Contents, and only these:

1. **Narrow the role CHECK to two values** (decision 166). `0002_users.sql:6` admits
   `('admin', 'member', 'guest')`. Drop that constraint and add
   `CHECK (role IN ('admin', 'member'))` — preceded by a `DO` block that RAISEs, naming the
   offending ids, if any `role = 'guest'` row exists. A bare `ADD CONSTRAINT` would also fail, but
   with a message the operator cannot act on; the assertion is what `cs-09` asks for and it is
   louder. Do **not** invent a conversion rule (disable them? re-role them?) — that is a data
   decision the findings do not support, and a fresh install has no such rows because the wizard
   only ever sent `'member'`.
2. **The password lockout columns** step 14 needs:
   `password_failed_count integer NOT NULL DEFAULT 0` and `password_locked_until timestamptz` on
   `app_user`, mirroring the PIN pair at `0002_users.sql:17-18`, with a comment citing §3.2 and
   saying why the PIN's lockout design is reused rather than a second scheme invented.
3. **Nothing else.** Everything §6.6's row editor writes already exists: `role`, `is_active`,
   `password_hash`, `must_change_password`, `pin_hash`, `jellyfin_user_id`. `cs-24`'s
   `nag_snoozed_until` belongs here **only if the owner picks branch (a)** in step 19.

**Ordering risk.** Several pre-release milestones will each want "the next migration". 0016 is
claimed by M4.6 here; a sibling milestone developed in parallel must take 0017 or later, and the
numbers are settled by **merge order, not plan order**. If M4.6 merges second, renumber this file
before merging — that is legal because it has not been applied yet — and never after.

**One consequence of `DELETE` worth naming rather than discovering.** `session.host_user_id`
(`0013_tonight.sql:30`) is `ON DELETE CASCADE`, so deleting a member deletes every Tonight session
they hosted, including the other member's `session_participant`, `session_answer` and
`session_result` rows. `session_participant.user_id` (`:76`) is also CASCADE, which is the only
correct behaviour there — `SET NULL` would violate
`session_participant_guest_has_no_user` (`:91-92`) by turning a member's seat into a guest seat. §6.6
distinguishes disable ("the account and its Ledger kept") from delete, so a destructive delete is
the spec's own intent; the UI must say what is lost before it asks for confirmation, and the roster's
delete control should read as the second step after disable, not an alternative to it.

## 8. Risks and gotchas

**The path parameter must be `{user_id}`.** `test_api_gating.concrete()`
(`backend/tests/test_api_gating.py:38-40`) rewrites exactly `{user_id}` and `{title_id}`. A new route
spelled `{id}` makes the parametrised sweep request a literal `/api/admin/users/%7Bid%7D`, which
answers 404 where the test asserts 403 — and the failure will read like a gating bug.

**Never edit an applied migration.** `0002_users.sql` is checksummed; a mismatch is a hard startup
error, not a warning. Everything in §4 goes in 0016.

**Raising `current_milestone` arms every M4.6 row at once.** Write all the rows first, then raise it,
then work down the red list. Do not lower it to get a green run, and do not add `waived` — an open
milestone's red gate *is* the test plan (`docs/TESTING.md`).

**A green no-DB run has not run this milestone.** Integration tests skip silently without
`TEST_DATABASE_URL` (auto-loaded from `.env.test`), and nearly every row here is integration. Bring
the DB up with `docker compose -f docker-compose.yml -f ops/compose.dev.yml up -d db` — overlays are
never auto-loaded, so pass each `-f`.

**The 19 `setup/members` call sites move in one commit.** Splitting them leaves the e2e suite dead at
`e2e/helpers.js:178`'s first `createMember`, and `ops/devstub.py:209` — a harness, not the app — must
move with them or the fixture-backed dev API diverges from `api/`.

**Deleting a user takes Tonight history with it.** `session.host_user_id` is `ON DELETE CASCADE`
(`0013_tonight.sql:30`), so deleting a member deletes every session they hosted, including the other
member's answers and ballots. Say so in the confirmation copy.

**Two argon2 changes interact.** Step 14's `Semaphore(4)` plus `to_thread` serialises the suite's many
argon2 calls; watch for timeouts in tests that create several accounts in a row. And step 22's
counting wrapper must be installed where `to_thread` still routes through it, or the structural
enumeration assertion silently counts zero.

**`asyncio.to_thread` and the PIN counter.** `check_pin`'s design comment (`core/auth.py:128-132`)
exists because a read-modify-write lets ten concurrent guesses cost one failure. Moving the verify
off the loop widens that window, not narrows it — keep the increment in SQL.

**`power()` returns double precision.** `interval * double precision` is valid; step 6's
`least(pin_failed_count + 1 - $2, 6)` must be inside `power()`, not around the interval, or the
overflow survives.

**WebAuthn binds to the origin.** The e2e run is against `http://localhost:8080` (= `PUBLIC_URL`),
never `127.0.0.1:8080` — same server, different origin, passkeys fail. Step 10 and step 15 both touch
the ceremonies; do not let a debugging detour change the host.

**`05-milestones.spec.js` will not warn you.** Unlike the surface placeholders, the admin-tab
assertion stays green when Users ships. Step 23 is a deliberate edit, and if it is skipped the suite
will happily report success on a spec whose whole purpose is to fail at this moment.

**House rules that bite here.** Line length 108 — §6.6's amended Users sentence is long and must be
