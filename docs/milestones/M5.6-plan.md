# M5.6 — Admin · Data: the board, the flywheel, the ledger editors, the rejects

> **This is a proposal, not an amendment.** Decisions **326, 328, 329, 330** and **336, 341, 342,
> 344, 345** are recorded in
> [`ROADMAP-M5.md`](ROADMAP-M5.md#decisions-the-owner-must-take-numbered-from-321). Four of them are
> blocking, and two of them (**328**, **329**) decide whether two of §8.4's four feeds can be
> implemented at all. Only **M5.1** edits the spec file.

§6.6's Data card is one page carrying four promises (`docs/spielplan-spec_v2.1.md:322`):

> "artifact-bundle import wizard (validate -> report -> hot-swap; §10), **acquisition pipeline
> monitor (per-title stage board from `acquisition_job`)**, **extraction queue (§8.4) with
> approve/spend controls**, **review of DNA rejects and low-evidence tags** — **ledger editors**
> writing the TSV formats the corpus project already uses: `adjudications_v1.tsv` for DNA verdicts
> *and* `corrections_v1.tsv` for credit facts, so app-side fixes survive every future re-derive."

One of those four is shipped. The page today renders five sections and none of them is an
acquisition board, a flywheel, a reject review or a ledger editor.

A queue fed automatically is only an instrument if a person can read it and spend against it, and
§8.4's whole flow — *"Admin reviews the queue, picks a batch and providers, sees the cost estimate,
launches"* (`spec:402`) — is one interaction on one page. That is why the board, the flywheel, the
editors and the rejects are one milestone: they are four cards on one file, and the file-locality
test gives that file one owner.

---

## 1. Why these are one milestone

**Four cards, one page, one hotspot file.** `frontend/src/routes/admin/data/+page.svelte` is 305
lines and would otherwise be edited by four agents. The house pattern is one component per card —
`BundleImport.svelte` and `DataSources.svelte` are already exactly that — so the page's own diff
stays small while each card is its own file.

**The flywheel's consumer and its feed are the same decision.** §8.4 lists four feeds and M5 can
supply at most two; which two, and on what threshold, is decisions 328 and 329. Splitting "the queue"
from "what fills it" would ship a queue whose emptiness nobody can diagnose.

**The reject review needs the ledger editor beside it.** §6.6 puts them in one clause for a reason:
an operator who sees a term dropped as out-of-vocabulary acts by writing an adjudication, and an
operator who sees a wrong credit acts by writing a correction. Two surfaces, one workflow.

**Depends on:** M5.1 (the board's data and its read routes), M5.3 (the derive the ledger editors
feed, and the `origin` column), M5.4 (`dna_reject` and the thin-facet measurement), M5.5 (the cost
estimate the Launch button needs). **Parallel with:** M5.7 — they share no file, and between them
they own every frontend admin page M5 touches.

## 2. What does not exist today

### 2.1 The Data page's own docstring claims a placeholder that is not rendered

`frontend/src/routes/admin/data/+page.svelte:6`: *"The acquisition board and the flywheel arrive with
M5 and say so."*

They do not say so. The rendered page is five sections: `<h1>Artifact bundle</h1>` (`:65`),
`<h2>History</h2>` (`:137`), `.rebuild` (`:154`), `.terms` (`:172`), `.axes` (`:208`). `grep -n "M5"`
over the file returns **line 6 and nothing else**. There is no acquisition board, no flywheel queue,
no DNA-reject review, no ledger editor, and no M5 placeholder of any kind.

That is a small live inaccuracy in the tree today, and it is worth naming because it means **this
milestone has no placeholder to delete** — unlike M4.6, whose Users tab killed an "arrives with M5"
assertion by design. `e2e/specs/05-milestones.spec.js`'s `PENDING` list (`:15-18`) carries only
`/map` and `/taste`, both M6.

### 2.2 `flywheel_item` has existed since migration 0004 with zero readers and zero writers

`0004_dna.sql:156-170`:

```sql
CREATE TABLE flywheel_item (
    id          bigserial PRIMARY KEY,
    kind        text NOT NULL
                CHECK (kind IN ('empty_predicate', 'uncovered_frontier',
                                'unnamed_residual', 'thin_facet')),

    est_cost_usd numeric(10, 4),
```

`grep -rn flywheel backend/spielplan/ frontend/src/ ops/ e2e/` returns **no INSERT, no SELECT, no
route and no component** — only four comments (`home/rail.py:382-383`, `placement/features.py:77`,
`:125`, `placement/contract.py:24`) and `test_backup.py:113` listing it under `APP_STATE`.

The four `kind` values are §8.4's four feeds, **already frozen by a CHECK in an applied,
checksummed migration**. So the schema has taken a position the spec has not defended, and striking
one of them (decision 328) costs a new migration.

**Two of the four have no producer until M6.** `empty_predicate` comes from §6.4's compositional
search and `uncovered_frontier` from the explore-frontier cache — `Job("explore-frontier-cache",

`/map` is a `Milestone.svelte` placeholder. M5 builds the consumer; M6 supplies those two inputs.

### 2.3 One M5-owned hook already exists and already promises a write

`home/rail.py:381-384`:

```python
    """`parse → predicate has(robots) · 0 survivors → flywheel` (§6.7, §6.4, §8.4)."""
```

### 2.4 `acquisition_job` has a board's shape and no reader

`0005_ledger.sql:133-142`. `reason` is commented *"shown verbatim on the admin board"* (`:138`) and
`retry_after` *"§8 stage 4: 30-day review-accrual window"* (`:139`). Both are read by nothing.
`acquisition_job_status` is indexed `(status, updated_at DESC)` (`:142`) — the board's own query,

M5.1 ships the read routes (`api/acquisition.py`, read-only). **Retry, retry-from-stage-N and

`parked` is already overloaded: `placement/reconcile.py:370-375` parks thin-but-successfully-placed
titles at stage 2 and its docstring says *"The title is ready — placed, badged, visible. It is the

title is broken.

### 2.5 The three ledger editors do not exist, and the third has nothing to edit

* **`adjudications_v1.tsv`** — `dna_adjudication` is loaded (`importer/dna.py:223-329`) and, until
  M5.4's verifier, read by nobody.
* **`corrections_v1.tsv`** — `credit_correction` is loaded (`:727-781`) and, until M5.3's applier,
  read by nobody. `importer/dna.py:767` records it: *"grep finds exactly two readers of
  `credit_correction`: this writer and `backup/movie_data.py`."*
* **The per-facet axis TSVs** — §6.4 (`spec:305`) is explicit: *"**No such file has been authored yet
  and the corpus bundle ships none** (decision 173)"*. Confirmed by listing
  `artifacts/dna_vocab/v1/`: it holds `vocab_<facet>_v1.tsv`, `vocab_pacing_axes_v1.tsv`,
  `alias_map_v1.tsv`, `adjudications_v1.tsv`, `s_matrix_v1.tsv`, `projection_capped_v1.txt`,
  `s_rejections_v1.tsv`, `veto_overrides.tsv` and `VOCABULARY.md` — and **no `mood.tsv`**. So
  editor 3 is an editor over an empty set, for a surface (§6.4, the Map) that §12 puts at **M6**, and

**And there is no writer for any of the TSV formats.** The loaders parse them; nothing serialises
back out. Decision 326 decides whether the editors write Postgres rows with a provenance column and
export TSV on demand, or write files — and **the collision is already recorded**: decision 171's Cost
paragraph (`ROADMAP-to-M5.md:390-412`) says *"an in-app-authored correction absent from the next
bundle's TSV is wiped (probed: P4 removed the app row)"*, because `importer/dna.py:759` is an
unscoped `DELETE FROM credit_correction`.

### 2.6 There is no reject store, and "low-evidence" cannot mean what it sounds like

`grep -rn dna_reject backend/` returns nothing; **M5.4's migration `0027` creates it** under decision
341. Until then §6.6's "review of DNA rejects" has no table, because §8 stage 7 drops and never
writes.

"Low-evidence tags" is constrained by §4.1 rule 2 — *"`salience`, `confidence`, `n_sources` are
**weights, never filters**. No `WHERE confidence > x` anywhere"* — and the guard
(`test_landmine_guards.py:56-61`, `:613`) catches the Python spelling too. So the review screen must
**order** ascending by confidence and never filter on it. That is a real UI constraint: no
"show only below 0.5" control, ever.

### 2.7 Nothing defines two of §8.4's four feeds

* **`unnamed_residual`.** The phrase "unnamed taste residual share" appears in the whole normative
  file **once**, in §8.4 itself (`spec:402`). "Residual" at `spec:223` means the per-title Ledger
  residual, which is a different thing. The vendored `ARCHITECTURE-extracts.md` carries §3 and
  Appendix C only (decision 294) and no nameable-variance metric. **Decision 328**, and the honest
  options are "vendor the definition" or "strike the feed" — not "invent a threshold".
* **`thin_facet`.** Four different "thin"s are in play: `placement/features.py:90-109`'s per-block
  `is_thin`; §5.3's "2 lack keywords, 3 lack any DNA row"; §4.1's forward reference to "§8's thinness
  test" which §8 never defines; and §8.4's per-facet coverage. §14 risk 2 names the measurement —
  *"measure facet coverage of post-2025 titles"* (`spec:485`) — and no threshold exists.
  **Decision 329.** M5.4 supplies the measurement; this milestone supplies the queue and needs the
  number.

### 2.8 One fact that makes the flywheel legible, and the spec never states it

§8.4 ends *"breadth being the measured binding constraint (zero owned titles carry
`themes.robots`)"* (`spec:402`). Read carelessly that says the vocabulary lacks the term and the
flywheel must grow it — which decision 163 forbids.

**`themes.robots` is a real vocabulary-v1 term.** `artifacts/dna_vocab/v1/vocab_v1_all.tsv:166`
carries it (582 terms plus a header), split from `themes.artificial_intelligence` in the "gap-fill
v1.1 2026-08-21" pass. So "breadth" means **coverage of existing terms across titles**, the sentence
is a statement about the library rather than the vocabulary, and the flywheel is possible. Put this
in the flywheel module's docstring; without it the feature reads as impossible.

**Decision 329 — define `thin_facet`.** Blocks Phase C and it is the **one feed M5 can definitely

the same amendment.

**Decision 326 — where the ledger editors write.** Blocks Phase D and is jointly owned with M5.3,
which lands the `origin` column in `0026`. Evidence: decision 171's recorded collision.

**Also relevant, takeable as the work proceeds:** **336** (`parked` vs `failed` and which actions each

## 4. The work, in order

Phase A is the board, because it is the card whose data is already complete. Phases B-D can follow in
any order. Phase E is the page itself and lands last, so the page is edited once.

### Phase A — the acquisition board

**A1. `AcquisitionBoard.svelte`**, in the `BundleImport.svelte` pattern: one card, one component,
fetching from M5.1's `GET /api/admin/acquisition`.

**A2. Ten segments, §8's names verbatim and in order** — `identify · enrich · derive · reviews gate ·
dna pack · dna extract · verify · project · place · ready`. One tuple, shared with the backend's
`acquire/pipeline.py::STAGES`, so the two spellings cannot drift. Proposal 136
(`spec-v2.2-proposals.md:1617`) argues the clause; whether §6.6 gains it is decision 330's business,
but the code holds one list either way.

**A3. The parked job's reason, verbatim.** `0005_ledger.sql:138` says *"shown verbatim on the admin
board"*, so no truncation and no re-phrasing. A reason like "reviews gate: 2 sources, 38 words —
retry window 30 days" is the product.

**A4. `parked` and `failed` render differently**, per decision 336 — a thin-but-placed title
(`reconcile.py:368-403`) is not a broken one.

**A5. The actions**, per decision 330 (proposal 109): retry stage / retry from stage N / abandon.
Each is a POST in **`api/acquisition.py`**, which M5.1 created read-only; this milestone adds the
writes and raises that module's `ALLOWED_RESIDUE` entry with them.

**A6. A stage-6 retry that would breach the cap is refused with that reason shown, never queued
silently.** The refusal lives in M5.5's spend module; this card renders it.

**A7. A link to the raw-document ledger, not to the bytes** (decision 345). `test_static_contracts.py:
1118` pins the worker's volume list and M4.7's sec-08 keeps `/data/raw` off the backend.

### Phase B — the flywheel's writers

**B1. `flywheel/` package** — `enqueue(kind, detail, reason, est_titles, est_cost_usd)` and the
queue's readers. The `reason` column is *"shown verbatim in the admin queue"* (`0004_dna.sql:161`),
so the writer composes the sentence.

**B2. `thin_facet`**, per decision 329, over M5.4's facet-coverage measurement. The write happens
**at the moment the condition is observed** — at the end of a title's stage 8 — not in a nightly
sweep. Coverage row `...flywheel-enqueues-naming-failures` asserts exactly that: *"appends a flywheel
row carrying its reason at the moment it happens and is readable from the admin queue immediately,
not after a nightly job"*.

**B3. `unnamed_residual`**, only if decision 328 defines it. If it is struck, the migration widening
the CHECK is this milestone's `0029`; if it is deferred, write nothing and say so in the module
docstring.

**B4. `empty_predicate` and `uncovered_frontier` get their writers but no callers.** M6's
compositional search and frontier cache are the producers. Export
`flywheel.enqueue_empty_predicate(...)` and leave it uncalled, with a docstring naming M6 — the same
shape `worker.py` uses for a registered job with no `run`. **Then** `home/rail.py:381-384`'s
`→ flywheel` tail is a promise the app can keep the day M6 calls it.

**B5. `home/rail.py`** is this milestone's only backend hotspot outside `flywheel/`. The change is
small: nothing about `parse_line`'s string, only that a caller now also writes.

### Phase C — the flywheel's surface

**C1. `FlywheelQueue.svelte`** — all four feeds shown, each labelled with its reason, each row
selectable.

**C2. Selection shows a running total against the remaining cap**, computed from M5.5's per-title
estimate x pass count x provider count. §8.4's "sees the cost estimate" is a *batch* total, and
that asymmetry matters: the per-title estimate §6.6 demands "before enabling" is reassurance, while
the batch total is the control. One click can select 19,071 rows.

**C3. Launch is disabled with its reason when the total would exceed the cap** — disabled, not a
warning after the fact.

**C4. Providers and pass count are chosen per batch**, per proposal 104 under decision 330.

**C5. A launched batch targets exactly the selected rows and no others** — the coverage row's second
clause, and the reason the batch needs an identity (a join table, or `status='approved'` plus a batch
id in `detail`; see §5).

**C6. Estimates recompute when the pass count changes.** Coverage row
`map-taste-admin-cost-estimate-before-enabling` (`:3153-3159`) asserts it and it is M5.7's row — but
the flywheel half is rendered here. Coordinate with M5.7: one estimate function (M5.5's), two
callers.

### Phase D — the ledger editors and the rejects

**D1. `LedgerEditor.svelte`, instantiated separately per ledger.** Proposal 105
(`spec-v2.2-proposals.md:1271`) argues *"Three separate editors with separate semantics, never one
merged 'corrections' screen"*, and the coverage row asserts *"three separate editors write three
separate artifacts with no merged write path"* (`:3166`). §14.5 makes the separation load-bearing:
DNA verdicts apply at ingest, credit facts apply last at every derive.

**D2. Each editor shows its rows, its provenance and the derive that will re-apply it** (proposal
105's own clause). With decision 326's `origin` column, "provenance" is a real field rather than a
guess.

**D3. The third editor**, per decision 342. If it ships, it edits an empty set for an M6 surface; if
it does not, the plan says so and §6.6's clause is narrowed or the editor is scheduled at M6 with
§6.4.

**D4. `DnaRejects.svelte`** over M5.4's `dna_reject`, **ordered ascending by confidence and never
filtered on it** (§4.1 rule 2, `test_landmine_guards.py:590` and `:613`). Each row shows the term,
the quote, the salience and the rule violated, so the operator can act by writing an adjudication —
which is the workflow that puts D1 and D4 on the same page.

**D5. No repair path.** §8 stage 7: failures drop, never repaired. The reject screen's only action is
"write a ledger row", never "accept this tag".

### Phase E — the page

**E1. `admin/data/+page.svelte`** gains four `<section>`s, one per component, in §6.6's own order:
bundle (shipped), board, flywheel, rejects, editors. The page's diff is imports and markup; every
behaviour is in a component.

**E2. Fix the stale docstring at `:6`.** It claims a placeholder that is not rendered; after this
milestone it should describe what the page has.

**E3. 48 px touch targets** — `test_static_contracts.py:135` guards them, and the phone is the
primary form factor (`e2e`'s `phone` project, iPhone 13/WebKit). A batch-selection checkbox is
exactly the control that gets drawn at 16 px.

**E4. `ops/devstub.py`** gains the new routes; `test_devstub_contract.py:64` compares its path set to
the app's.

**E5. e2e.** M5.6 and M5.7 should claim their spec-file numbers in one block, agreed between them —
the suite is filename-ordered, single-worker and stateful, and `e2e/specs/` currently runs to 19
numbered files. Do not parallelise, and do not renumber an existing file.

## 5. Schema changes

**`0029_flywheel.sql`, or none.** Take the number from
[`ROADMAP-M5.md`'s ledger](ROADMAP-M5.md#the-migration-ledger).

Three candidates, all conditional:

* **A batch identity** for C5's "targets exactly the selected rows". Cheapest honest form: a
  `flywheel_batch(id, created_at, providers, passes, est_cost_usd, launched_at)` plus a
  `flywheel_item.batch_id`. The alternative — a batch id inside `detail` jsonb — works and is harder
  to query; prefer the column.
* **The CHECK widening**, only if decision 328 strikes `unnamed_residual` or decision 344 adds an
  `absent_term` kind. `flywheel_item`'s CHECK is in applied, checksummed `0004_dna.sql:158-160`, so
  either change is a new migration with a `DROP CONSTRAINT` / `ADD CONSTRAINT` pair.
* **Nothing at all**, if the batch lives in `detail` and no kind changes. **Say so explicitly** —
  M4.8, M4.10, M4.11, M4.12, M4.15 and M4.16 all wrote no migration and three of them said so, which
  `ROADMAP-to-M5.md:288-290` names as the behaviour to copy.

`dna_reject` is **M5.4's** `0027`; the `origin` provenance column is **M5.3's** `0026`. This
milestone consumes both.

**Check `backup/movie_data.py` before adding a table.** `test_backup.py:113` lists `flywheel_item`
under `APP_STATE`, so a new table beside it needs the same treatment or a restored archive loses the
batches.

## 7. Exit criterion, as something to run

> On a real install with the real corpus bundle: a title whose extracted-tier facet coverage falls

  uncalled.
* **It does not build the explore-frontier cache.** `Job("explore-frontier-cache", "M6", …)` at

  queue depth, last syncs and logs are **M5.7's**.
* **It does not build the verifier or the reject store.** `dna_reject` is **M5.4's** table; this

## 9. Risks and gotchas

**`flywheel_item`'s four `kind` values are frozen in an applied, checksummed migration.** Striking one
or adding one costs a migration. Decide 328 and 344 before writing SQL, not after.

**"At the moment it happens" is a real-time write on a read path** and the coverage row asserts it
explicitly. A nightly sweep that fills the queue passes every naive test and fails the row.

**The cap's asymmetry should shape the surface.** The per-title estimate is reassurance; the batch
total is the control. Getting this backwards ships a page that reassures an admin while they select
19,071 rows.

**`parked` is overloaded and one of its meanings is "everything is fine".** `reconcile.py:368-403`
has been writing that meaning since M4.13. A board that does not distinguish them reports the
library's thin backlog as breakage.

**`reason` is rendered verbatim, so the *writer* composes product copy.** M5.1's driver and M5.3's
gate write those strings; if they read badly on the board, the fix is upstream.

**§4.1 rule 2 forbids a filter control, not just a WHERE clause.** A "hide low confidence" toggle in
Svelte is the same cut, one layer up. The static guard reads source files
(`test_landmine_guards.py:56-61`) and it was taught the Python spelling for exactly this reason.

**The third editor edits an empty set.** If decision 342 puts it in M5, say in the UI that no axis
file has been authored — the same honesty §6.4 already shows (`spec:305`).

**`e2e/specs/` is filename-ordered, single-worker and stateful.** Number the new files into the
sequence with M5.7, and run `npm --prefix e2e run fresh` rather than bare `playwright test` — the
two phases plus the backend restart are load-bearing, and a plain run against a used stack
fake-passes.

**The `phone` project (iPhone 13, WebKit) is the primary form factor** and a batch-selection UI is
the easiest place to ship a 16 px control. `test_static_contracts.py:135` guards 48 px.

**Line length 108, ASCII in console output, Svelte 5 runes and JS not TS.** Shared state in
`.svelte.js` modules with colocated `*.test.js`; relative `/api` URLs only.
