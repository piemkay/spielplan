## Why this milestone exists

Three agents investigated the owner's architecture change — a corpus survey, a Spielplan
coupling map, and a skeptic told to refute what the first two suggested. **Every finding below
was re-verified by hand** against the real bundle at
`movie_data_curator/data/export_bundle/v20260828/` before being written down.

### 1. The id design I was about to recommend is arithmetically wrong

The proposal was: adopt the corpus ids at seed time, then seed a sequence above the imported
maximum and mint from there. It rests on "the corpus never ships content again."

```
content.sqlite  sqlite_sequence:  title 21442   person 114503
                title max/count:  21442 / 19071
```

The corpus's next minted title id is **21443**. "Above the imported maximum" starts Spielplan
at **21443**. And the model bundle still carries content ids — `backbone.npz.title_id`,
`review_text_emb.npz.title_ids`, `seed_list.json`, `corrections_v1.tsv` are all keyed by corpus
`title.id` and all travel in `artifacts/`. One newly crawled film, and the next model bundle
asserts things about id 21443 while Spielplan's 21443 is a title the household acquired from
Jellyfin. `Backbone.row_of` resolves it, `classify_warm` stamps it warm, §5.1 scores it against
another film's embedding — and nothing trips, because `backbone.py:164` only checks that the
ids ascend, which they still do.

**What survives: partition the namespace, and assert the boundary.** Corpus ids stay verbatim,
because four read paths are id-keyed and the two artifacts with no id vector — `content_X.npz`
and `item_priors.npz` — cannot survive a permutation they have no way to check. Spielplan mints
from a **disjoint** range, so collision is impossible by construction rather than contingent on
the corpus standing still, and the importer refuses a bundle that reaches into Spielplan's
range. Range partitioning still cannot see the corpus *merging* two titles — which changes what
an id means without changing the id — so the model bundle also carries an identity column
row-aligned to `title_id`, and the importer checks it.

### 2. Three live defects on `main`, none caused by the architecture change

**The Cold Tower's credit block has been silently empty in every placement ever computed.**
`placement/features.py:253` keys it on `person_id::text`; the shipped `feature_contract.json`
names those 244 columns `p:director:Adam Arkin`, `p:composer:A.R. Rahman` — by name. Every key
misses, and the miss is invisible by construction: `features.py:96` marks the block `present`
because the query returned rows, counts the misses into `BuiltVector.unmapped`, and
`reconcile.py`'s `_UPSERT` never persists `unmapped`. Nothing is `dropped`, `is_thin` stays
False, no acquisition job parks. Cast and director contribute nothing to any coordinate.

**The real bundle cannot be imported at all.** `seed_list` is a total name collision — the
corpus's is a 238-row *list registry* (`id, slug, name, source, kind, category, weight,
item_count, fetched_at, notes`), Spielplan's is `position, title_id, decade`, and
`load.py:157` maps one onto the other, which COPYs 238 all-NULL rows into a NOT NULL primary
key. `corrections_v1.tsv`'s real header is `kind, title_id, value, evidence, note` while
`dna.py:232` reads `r["field"]` — an uncaught `KeyError`, not a `report.fail`.
`feature_contract.json`'s real top level is `content_blocks` plus a flat 6,435-entry
`feature_names` list; the fixture writes `blocks` plus a dict.

**Three shipped tables are loaded by nothing, and the report cannot say so.** `title_meta` —
named in §4.1's own table list, tabled at `0003_content.sql:72`, **46,318 rows** — appears
nowhere under `backend/spielplan/`. `title_list_membership` (35,295) and `imdb_ratings`
(14,858) likewise. They vanish without a report line, because `ImportReport` tracks unmapped
*columns within mapped tables*; an unmapped **table** is invisible.

### 3. How all of it survived, in one line of one test

`backend/tests/test_placement.py:578`:

```python
assert vec[contract.block("credit").column("3")] == 1.0
```

The fixture's contract declares the credit column as `"3"` — the person id the builder emits.
The test is named *"the vector is built from the database through the contract's own columns"*,
and the contract is the fixture's, whose columns were invented to match the code. Line 594 then
asserts `set(built.unmapped) == {"meta"}` — that credit has **no** unmapped keys — which against
the shipped contract would be 244 misses out of 244.

This is M4's lesson one level up. `M4-open-points.md` §5 names five patterns for a test that
cannot fail; the fifth is *a test that scores the implementation with the same function the
implementation optimises*. A fixture written from the same reading as the importer is that
same failure at the level of the artifact: it tests the reading, not the world.

`README.md` says *"The corpus bundle does not exist in this repo, so the importer is verified
against a synthetic fixture."* It does exist, built 2026-08-28. That sentence is the root cause
and it gets corrected here.

## What the review changed

A Fable 5.1 reviewer was given the whole branch diff and told that a review finding nothing is
not a review. It confirmed every headline fact — `primary_title`, the `dna_evidence` keying,
the `p:<role>:<name>` grammar, `sqlite_sequence` at 21442, the unloaded tables, the id
collision — and then found the milestone **correctly premised and badly scoped**. Four
corrections, each verified again by hand before being accepted:

**1. It is not the credit block. It is all nine.** Every block in the shipped contract carries a
prefix — `kw:`, `dna:`, `g:`, `p:`, `genre:`, `country:`, `lang:`, `decade:`, `runtime:`,
`award:`, `kind:` — and `placement/features.py` emits bare keys for most of them and
`person_id::text` for credit. Measured: 0 of 84,876 credit keys hit, 0 of 97,287 keyword
columns, 0 of 1,128 genome tags, 0 of 656 genres. Against the real contract the tower would
receive the 64 text columns and about a dozen meta columns out of 6,499. The row is rewritten
from one block to nine; a milestone closed on the old row would have left seven blocks
structurally zero and parked every title for an enrichment that cannot fix a key grammar. The
reviewer was also right that "empty in every placement ever computed" was rhetoric: every
placement ever computed was against the fixture, where the keys match by construction.

**2. The model half of the bundle is unloadable too, and no row said so.** `cold_tower.pt` is a
bare `OrderedDict` state_dict; `tower.py:136` requires a dict carrying `state_dict`, `version`,
`arch` and `input_dim`, so the Cold Tower cannot be constructed at all — the stage §12's M5
exit criterion runs through. `backbone.npz` and `review_text_emb.npz` ship `title_ids` where the
loaders demand `title_id`. `text_scale` lives at `text_block.text_scale` (2.6055), not at the
top level. `artifacts/manifest.json` carries no `bundle_version`, so every real bundle would be
named "unknown". New row.

**3. The vocabulary layer is written against files that do not exist, and the validator dies
before it can say so.** The app reads `terms.tsv` / `aliases.tsv` / `adjudications.tsv`; the
corpus ships per-facet vocab TSVs, `alias_map_v1.tsv`, and an `adjudications_v1.tsv` keyed *per
title*. `dna_tag` and `dna_projected` both reference `dna_vocabulary(version)`, so nothing in
the naming layer loads. And the content validator raises `OperationalError: no such column:
e.dna_tag_id` — the operator gets a stack trace where §10 promises a report, and every genuine
failure after that point is never reached. Two new rows. The unloaded-table count is seven, not
three: add `dna_annotation`, `dna_term_signal`, `dna_exclusion` (all three named in §10's own
manifest line) and `dna_projection_run`.

**4. The title-card row invented a rule the corpus contradicts.** It said a dropped source falls
back a *whole block* rather than mixing fields. `mdc/export.py:34-45` resolves **per field**, via
`_best` over a documented `SOURCE_PRIORITY`, with `mpst` last on purpose because its synopses
give the ending away. Per field is also what the data requires: tmdb has tagline and poster and
plot, omdb has poster and no tagline, wikipedia is the only source with `plot_short` — a
whole-block rule blanks fields another source has. §4.1's "one block = one droppable source" is
a storage invariant, not a rendering rule. Row corrected, and the order will travel with the
bundle rather than being hard-coded here. **This answers the first of the two decisions that
were about to be taken by default, and answers it against what I was going to do.**

**Three defects in this branch's own new test**, all fixed in the same commit and worth naming
because two are the exact failure the file exists to prevent:

- `theirs <= ours` on the contract's key set let the fixture *add* the shipped keys while
  keeping `blocks`, so the test would go green while `contract.py` still read `blocks` and
  still rejected the real file. Now equality.
- the block-grammar assertion compared only `p:` patterns — the narrow check that missed
  finding 1. Now every block's grammar, `ours <= theirs`.
- and that widened assertion then **passed vacuously**, because the fixture's `feature_names`
  is a dict, so the extractor yields an empty pattern set and the empty set is a subset of
  everything. Now guarded by a non-emptiness assertion. A test that could not fail, written
  inside the test written to catch tests that cannot fail.

Seven of that file's assertions now fail, each for a distinct real reason.

**Answered: vocabulary migration is deferred, and made safe rather than silent.** The
reviewer's strongest design finding was that "content seeds once" contradicts §14 risk 7, which
routes vocabulary changes through bundle re-imports. Owner's call, 2026-09-01: a DNA vocabulary
change is a fundamental data migration and gets its own plan when it is needed, not a clause in
this milestone.

Deferring it is only honest if the deferral cannot bite silently, and this one could: a
models-only bundle shipping `dna_vocab/v2` would leave `dna_tag` and `dna_projected` at v1 while
the feature builder filters on the active version, so **both DNA blocks would go empty for every
title** — and empty is not an error anywhere in the read path. So the importer refuses a
vocabulary version change and names the missing migration. Row
`platform-vocabulary-change-is-refused-not-degraded`.

Both owner decisions are now written up as numbered entries — **decision 162** (the corpus
supplies models, content seeds once, Spielplan owns the ids) and **decision 163** (a vocabulary
change is a migration, not an import) — in `docs/spec-v2.2-proposals.md`, and the five rows that
rest on them cite `decision 162` / `decision 163` rather than a bare date. `CLAUDE.md` requires
work to cite its clause; a row citing "owner decision 2026-09-01" pointed at nothing.
