# M4.7 — the box: boot, secrets, jobs, backup and the image

**This milestone is not in §12.** Neither is M4.5, and §12's own note (spec line 419) already
establishes the shape: a milestone outside the table is legitimate when the table scheduled
nothing for work the release cannot ship without. This one exists because every operator-facing
promise in §2 — required config, secrets custody with rotation, a nightly dump with rotation 14,
a restore that works — is documented, coverage-mapped, and either unimplemented or implemented in
a way that fails on the day it is needed. Its thesis is one sentence: **make the install
survivable** — a restore that works, a wrong key that degrades instead of 500ing, jobs that
report their outcome, and an image that is CPU-only by pin rather than by ordering luck.

**Depends on M4.6.** Two hard couplings, not a preference. The restore drill asserts that *a
member's own* seen/verdict/prompt write still commits under an unreadable key, and "a member" is
an account only M4.6's Users surface can create (today `e2e/helpers.js` POSTs `/api/setup/members`
directly, which is exactly the blindness M4.6 exists to end). And `core/config.py`'s validator
block is shared: M4.6 lands the `session_days` / `admin_reauth_hours` validators (findings
`cs-45`, `dd24`), M4.7 lands the `public_url` / `session_secret` / `secrets_key` ones. Two
milestones editing one `model_validator` in sequence is fine; in parallel it is a merge conflict
in the file that decides whether the app boots.

---

## 1. Why these changes are one milestone

This is the operator's territory, and it is defined by five files no product milestone may touch:

| file | what it owns here |
|---|---|
| `backend/spielplan/app.py` | the lifespan block and the single exception-handler block |
| `backend/spielplan/worker.py` | the job registry, `due()` and `_tick` |
| `backend/spielplan/core/config.py` | the validator block |
| `backend/spielplan/core/secrets.py` | DEK custody and the AEAD boundary |
| `docker-compose.yml` | every line of which is mirrored by a guard in `test_static_contracts.py` |

The last pairing is the load-bearing one. `docker-compose.yml` and `backend/tests/test_static_contracts.py`
move together by construction: four findings in this milestone edit the compose anchor
(`ds01`, `dd-compose`, `ops-12`, `sec-08`) and four more rewrite the guards that read it
(`ddocs-08`, `tq3-one-published-port`, `dd28`, `arch-09`). Splitting them across milestones means
two branches editing the same twelve-line YAML anchor and the same six guard functions.
`ds01` and `ds07` say so explicitly in their own mitigations — "same diff as ds01, so the compose
anchor is touched once."

**Secrets custody is one fix with four faces.** `dd03` (unhandled `InvalidTag`), `ops-01` (the
restore runbook), `spec-08` (rotation documented three times, implemented nowhere),
`tq3-secrets-rotation-row` (an M0 row closed by a database-free unit test of an uncalled helper)
and `sec-10` (no AAD, two active DEK rows) are the same defect seen from five angles, and they
close in one diff: a typed `SecretsUnreadable`, one degradation in `registry.load_jellyfin`, a
`spielplan-secrets` executor, one drill. Split them and each half is either untestable or
dishonest.

**Two findings are dead until a third lands.** `ops-09`'s runbook line — "confirm the upgrade by
grepping the applied migrations out of `docker compose logs backend`" — cannot be written until
`ops-05` configures logging, because the backend process emits no INFO record at all. `ops-07`'s
worker liveness is invisible for the same reason: a successful tick logs nothing, so there is
nothing for a heartbeat to corroborate. Writing the runbook first produces a document that
instructs the operator to look for a line that does not exist.

**It runs second in the release sequence despite holding only ranks 8 and 9**, because it owns
the two seams five later milestones plug into:

- the app-level exception-handler block, which is where a unique violation becomes a 409 rather
  than a 500 "database error" (M4.10 and M4.12 depend on it), and where an `OSError`-family
  connection failure stops escaping as a bare traceback (`ops-12`);
- the worker job registry with a per-job timeout, a stop grace period and a persisted `job_run`
  row (M4.11, M4.13 and M4.14 depend on it). `ops-11` states the dependency in its own words:
  §6.6's System card "is an M5+ surface, but its data source has to exist before the surface can",
  and `ops-03`, `ops-04` and `ops-07` each need a place for their state to land.

**And one deletion turns into a prerequisite.** `dd-deploy-image-installs-deps-only-no-migrate-script`
found that the image installs `-r pyproject.toml` — dependencies only — so the declared console
script `spielplan-migrate` does not exist inside the container. Its preferred mitigation is to
delete the entry point. That option is closed here, because this milestone adds two more console
scripts the operator must be able to run inside the container (`spielplan-secrets` from `spec-08`,
`spielplan-movie-data` from `spec-07`). The Dockerfile must therefore install the project, and
the wheel must force-include `migrations/`. That is a coherence fact, not a preference: three
findings converge on one line of `ops/backend.Dockerfile`.

## 2. What is broken today

Each entry names the finding id in brackets, the evidence, what the code does, and what it should
do. Where two findings are one repair they are grouped under one number.

### Secrets custody

**1. A wrong or lost `SECRETS_KEY` boots green and then 500s every member write, including the
route that would fix it. [dd03-wrong-secrets-key-500s-member-writes-and-blocks-ui-recovery]**

`core/secrets.py:52` — `aes.decrypt(blob[:_NONCE], blob[_NONCE:], _INFO)` raises
`cryptography.exceptions.InvalidTag` under a different KEK. Nothing catches it: `app.py:114`'s
only handler is `@app.exception_handler(asyncpg.PostgresError)`. Executed as a full restore drill,
the observable state is: lifespan completes (because `push/keys.ensure_keypair` returns the
*stored* public half without unwrapping, `push/keys.py:81-83`), `/api/health` reports `ok: true`,
login and `/me` succeed — and then `POST /api/titles/{id}/state`, `POST /api/prompts/finish/{id}`,
`POST /api/rate/verdict`, `POST /api/rate/not-seen`, `GET`/`PUT /api/admin/connectors/jellyfin`,
`GET /api/admin/users` and the sync/poll/test routes all return 500. The call sites are
`api/state.py:34-35` (`jellyfin_for` -> `registry.load_jellyfin`, reached at :54 and :87),
`api/rate.py:105-106` (`_jellyfin`, evaluated as an argument at :196, :218, :270, :291), and
`api/admin.py:48, 58, 107, 159, 187, 195`.

The recovery path is dead too: `registry.save_jellyfin` begins with `current = await
load_jellyfin(conn)` (`connectors/registry.py:165`), and `secrets.ensure_dek` unwraps the active
row before it can seal anything (`core/secrets.py:62-63`), so an admin who regenerated `.env`
cannot fix custody from the UI at all. A second branch: on a database holding a DEK row but no
VAPID row, `push/keys.py:87`'s `except RuntimeError` does not catch `InvalidTag`, so it escapes
the lifespan and the container never starts — with a traceback that never names `SECRETS_KEY`.

It should raise a typed `SecretsUnreadable(RuntimeError)` naming `SECRETS_KEY` and the `key_id`;
`load_jellyfin` should catch it and return an unconfigured `JellyfinConfig` so §3.3's app-side
write commits with a truthful reason; and `save_jellyfin` should be able to seal under a fresh
DEK when the current row will not open.

**2. Connector ciphertexts carry no AAD, and concurrent first boots mint two active DEK rows.
[sec-10-secrets-custody-aad-and-dek-race]**

`core/secrets.py:89` and `:94` — `aes.encrypt(nonce, raw, None)` / `aes.decrypt(..., None)` —
while the DEK wrap at `:47`/`:52` uses `_INFO` as associated data. A ciphertext is therefore not
bound to its row: copying `jellyfin`'s `secrets_encrypted` / `secrets_key_id` into the `tmdb` row
makes `get_connector_secrets('tmdb')` return `{'api_key': 'JF-ADMIN-KEY'}`. Separately,
`ensure_dek` (`core/secrets.py:55-72`) is SELECT-then-INSERT with no lock, and
`0001_system.sql:13-18` carries no partial unique index on `retired_at IS NULL`; three concurrent
`ensure_dek` calls on separate asyncpg connections produced two active rows. Harmless for reads
today because every ciphertext names its `key_id` — but §2 speaks of "the one DEK row", and the
rotation and repair executors this milestone adds must both assume exactly one.

It should pass `aad = f'{table}/{name}'.encode()` through `put_/get_connector_secrets` and
`push/keys`, with a `None`-AAD fallback for rows written before the change and a re-seal on the
next save; and `ensure_dek` should `INSERT ... ON CONFLICT DO NOTHING` then re-SELECT, adopting
the winner exactly as `push/keys.py:98-107` already does for the VAPID pair, behind a new partial
unique index.

**3. `SECRETS_KEY` rotation is promised three times and implemented nowhere, and the coverage row
that certifies it is a database-free unit test of an uncalled helper.
[spec-08-secrets-key-rotation-documented-thrice-implemented-nowhere,
tq3-secrets-rotation-row-is-closed-by-a-unit-test-of-an-uncalled-helper]**

Spec line 58 ("rotating `SECRETS_KEY` is an explicit admin action that re-wraps the one DEK row"),
`.env.example:15-19`, and coverage row `platform-key-rotation-semantics`
(`spec_coverage.toml:76-82`, `kind = "integration"`) all describe a rotation. The only
implementation is `core/secrets.py:138-140`'s pure `rewrap_dek`, whose sole caller is
`backend/tests/test_secrets.py`; `grep -rn rewrap_dek backend/spielplan/ ops/` finds the
definition, the `__all__` entry and nothing else. `backend/pyproject.toml:39-40` ships
`spielplan-migrate` alone. The row's named tests take no `db` fixture and the whole file passes
with `TEST_DATABASE_URL` unset, which proves the `integration` label is nominal. An operator who
follows `.env.example` and edits `SECRETS_KEY` lands in defect 1.

It should get an executor and the row should become true rather than narrowed.

**4. Nothing generates `SECRETS_KEY` and nothing validates it; and the DEK first-boot row has no
integration test. [cs-44-secrets-key-neither-generated-nor-checked,
cs-46-dek-first-boot-row-has-no-integration-test]**

Spec line 58 names "the setup wizard / compose template" as the generator. Neither generates:
`api/setup.py`'s four write routes only call `require_secrets_key()`, `docker-compose.yml:13`'s
`${SECRETS_KEY:?}` enforces non-emptiness, and `.env.example:18` is an instruction. `Settings.secrets_key`
(`core/config.py:30`) has no length or entropy constraint and `core/secrets._kek`
(`core/secrets.py:33-41`) HKDF-expands any printable string into a valid KEK by design, so
`SECRETS_KEY=x` produces a fully working, fully green install whose KEK is guessable — guarding a
Jellyfin API key §14.3 calls unscoped and admin-equivalent. And row `platform-dek-aead-key-id`
(`spec_coverage.toml:93-100`) claims "first boot creates exactly one random 256-bit key" with
`kind = "integration"`, while three of its four tests are pure-function tests over `_wrap`/`_unwrap`
in a file with no `db` fixture and the fourth inserts a one-byte fake key. The "exactly one"
property — precisely what finding 2 says the code loses — is permanently green.

### Required configuration

**5. Empty `SESSION_SECRET` signs cookies with a repo-published constant, empty or scheme-less
`PUBLIC_URL` binds passkeys to `localhost`, and the coverage row claims this is validated.
[sec-03-config-falls-back-to-public-constants-outside-compose,
spec-04-required-config-row-overclaims-python-accepts-empty-public-url,
ops-10-required-config-enforced-only-by-compose]**

`core/config.py:25,27` — `public_url: str = "http://localhost:8080"`, `session_secret: str = ""`
— and the class carries exactly one validator, `_strip_trailing_slash` at `:57-60`. Three call
sites then fall back to a literal in the public repository: `core/auth.py:36`, `api/rank.py:67`,
`api/tonight.py:75` — `URLSafeSerializer(settings().session_secret or "insecure-dev-secret", ...)`.
`config.py:79` is `return urlparse(self.public_url).hostname or "localhost"`, so both `''` and
`spielplan.example.tld` (a hostname with no scheme — exactly what an operator writes when copying
a hostname rather than the template's URL) yield `rp_id = 'localhost'`, and every passkey
registered in that window fails in the browser with "the relying party ID is not a registrable
domain suffix". The only enforcement is `docker-compose.yml:11-13`'s `${VAR:?}`, which does not
exist for README's own "Developing" flow (host-run uvicorn), a systemd unit, or a CI job with a
blank env. Coverage row `platform-required-config-refuses-boot` (`spec_coverage.toml:84-91`) says
"Startup config validation rejects a missing or empty PUBLIC_URL" and its two named tests are a
grep of `docker-compose.yml` (`test_static_contracts.py:366-371`) and the `SECRETS_KEY` half.

It should be one `model_validator(mode='after')` that refuses an empty or scheme-less
`public_url`, a `session_secret` under 32 characters and a short `secrets_key`, citing §2 and
§14.4; the three fallbacks should be deleted; and the row should be made true rather than
narrowed.

### The HTTP seam

**6. `/api/health` answers 200 with `ok: false` when Postgres is unreachable, and all three
consumers key on the status code. [ops-02-health-200-with-ok-false]**

`app.py:99-112` catches every exception and returns the dict with no `status_code`.
`ops/backend.Dockerfile:58-59` is `curl -fsS ... /api/health || exit 1`, `.github/workflows/ci.yml:135`
is the same shape, and `e2e/run.mjs:46` fetches and does not read the body. A backend that cannot
reach Postgres is reported healthy by Docker, by CI's wait loop and by the e2e harness.

**7. Ten in-flight health probes exhaust the pool when Postgres hangs, and no acquire has a
timeout anywhere. [dd-health-probes-drain-pool-on-hung-db,
schema-pool-acquire-no-timeout-and-search-path-reset]**

`app.py:100-102` acquires and pings with no timeout; `db/pool.py:39-47` creates the pool with no
`command_timeout` and `db/pool.py:64-67`'s `acquire()` passes none. `max_size` is 10 and the image
HEALTHCHECK runs every 30 s: curl gives up at 5 s but the server-side coroutine keeps holding its
connection. Measured: with the ping blocked, 10 concurrent health requests took the pool to
size 10 / idle 0 and an 11th request to `/api/setup/state` did not answer within 4 s.
`api/deps.py:14-16` holds a connection for the whole request, so the same exhaustion is reachable
from real traffic with no 503 and nothing in the log. Separately `db/pool.py:26-27`'s
`SET search_path` is undone by asyncpg's `RESET ALL` on the first release — `SHOW search_path`
reads `public` on a fresh connection and `"$user", public` after release and re-acquire — so
`pool.py:19-21`'s "§4.1 rule 3: application connections keep it out of `search_path`" is kept by
the schema-qualified read at `db/library.py:391` and the landmine guard, not by the connection
setup that claims it.

**8. `/api/docs` and `/openapi.json` publish the whole route surface anonymously.
[sec-12-openapi-and-docs-served-unauthenticated]**

`app.py:83` — `FastAPI(..., docs_url="/api/docs")` with FastAPI's default `openapi_url`, both
registered before the SPA catch-all and behind no auth. The schema enumerates every admin and
setup route with its body shapes. `create_app().openapi()` (which `test_api_gating.py` uses) does
not depend on the URL, so gating the HTTP exposure costs the tests nothing.

**9. The backend process never configures logging: a real boot that applied every migration
printed none of `app.py`'s INFO lines. [ops-05-backend-info-logs-never-reach-docker-logs]**

`worker.py:23-25`'s `logging.basicConfig` is the only logging configuration in the repository;
`app.py` has `log = logging.getLogger("spielplan")` at `:39` and nothing else. Under uvicorn
0.52.4's `dictConfig(LOGGING_CONFIG)` the root logger is level 30 with no handlers and `spielplan`
inherits that, so INFO records reach neither stdout nor stderr while WARNING/ERROR fall through to
`logging.lastResort` — message only, no timestamp, level or logger name. A real
`python -m uvicorn spielplan.app:app` against a fresh database applied all 15 migrations and its
output contained only uvicorn's own lines: `app.py:50`'s "applied migrations", `:61`'s "no
web-push keypair" and `:74`'s "no artifact bundle active" were all absent, along with 20 other
`log.info` call sites including `connectors/registry.py:97`'s "env seed ignored (§2)".

### The worker

**10. No job outcome is persisted anywhere. [ops-11-job-outcomes-never-persisted]**

`worker.py:361` — `last_run: dict[str, float] = {}`. `worker.py:235-236` is
`report = await nightly.run(); log.info("backup: %s", report.as_dict())` and that is the only
consumer; `SyncReport`, `WatchReport` and the refit reports likewise. There is no table, no
`app_setting` row and no route that says when the last dump succeeded or how big it was.
`api/artifacts.py:57-66`, the payload the Data tab already polls, carries
`bundles/active/loaded/restart_required/import_dir/rebuild_set` and nothing else. Spec line 288
(§6.6) names "job health, queue depth, last syncs, backup status, logs" and
`backup/nightly.py:19-20` claims "the rotation, the report and §6.6's backup status line all live
in the app". The nightly backup can fail for a month with the only signal one ERROR per day in a
container log that (finding 9) carries no timestamp.

**11. "Rotation 14" counts files, not nights, and every worker start spends one.
[ops-03-nightly-means-since-worker-start, cs-10-nightly-is-uptime-not-a-night]**

`worker.py:292-304`'s `due()` makes a job that has never run due immediately — the docstring at
`:295-296` argues for it — and `last_run` is in-process, so a cold start fires all five
`every=86400` jobs at once: `nightly-backup`, `ledger-map-refit`, `fold-in-user-vectors`,
`placement-reconciliation`, `push-subscription-prune`. `backup/nightly.py:118-122`'s `prune` is a
pure count over the name-sorted list, so fourteen simulated restarts inside 21 minutes over a
directory holding fourteen nights left zero nights of real history. `dump_name`
(`backup/nightly.py:83`) is second-resolution, so two dumps started in the same second silently
overwrite one another. No wall clock is consulted anywhere: `settings().tz` appears once in
`worker.py`, in the log line at `:319`, and `ZoneInfo` appears zero times in the module — so
"nightly" means "every 24 h of uptime", and README's install and upgrade gesture is
`docker compose up`, which pins the whole batch to whatever evening hour the operator restarted.

**12. A failed job waits out its whole interval, and two load-bearing docstrings are false.
[ops-04-failed-job-deferred-a-full-interval]**

`worker.py:307-314` stamps `last_run[job.name] = now` *before* the call, so the comment at
`:313` — "One failing job must not take the loop down; the next tick retries it" — is wrong: a
nightly job that raises is not due again for 24 hours. Measured: a failed job ran once and was not
due again an hour later. And `backup/nightly.py:177-180` says the dump "goes to a thread — the
worker's other jobs share this event loop, and §7.3's one-minute playback poll is the one that
would notice", but `_tick` awaits due jobs sequentially, so a 0.5 s thread job delayed the sibling
poll by 0.502 s in the same tick.

**13. Worker liveness is invisible; the dump has no timeout; a successful tick logs nothing.
[ops-07-worker-liveness-unobservable]**

`docker-compose.yml:73-77` disables the inherited HTTP healthcheck — correctly — and replaces it
with nothing, so `docker compose ps` says "Up" for a worker whose loop is stuck.
`backup/nightly.py:160-163` runs `subprocess.run` with no `timeout=`, awaited via `to_thread`
inside the sequential `_tick`, so a `pg_dump` blocked behind an import's lock blocks the 60 s
`/Sessions` poll, the fold-in tick and the sync indefinitely. `worker.py:307-314` logs only on
failure: a successful tick emits zero `spielplan*` records even at DEBUG capture, so the log
cannot say when a job started, how long it took, or that the loop is alive.

**14. Shutdown is not graceful and compose declares no grace period.
[ops-08-no-stop-grace-period-for-minutes-long-jobs]**

`worker.py:353-359` sets a `stop` event from SIGTERM; `worker.py:362-369` checks it only between
ticks, so a running job is never cancelled. `grep stop_grace_period docker-compose.yml ops/*.yml`
returns nothing, so `docker compose stop/restart/down` SIGKILLs after Docker's 10 s default. §10
requires "restart backend + worker" after every import, `e2e/run.mjs` does exactly that, and
finding 11 puts the worker mid-nightly-set seconds after any start — with the corpus dump measured
at 35 s. A SIGKILL leaves a `.partial` (cleaned only by the next successful run's prune), skips
`close_pool()` and the "worker stopped" line, and leaves the child `pg_dump` running.

**15. Every model job runs numpy/torch on the loop thread, and `tower_threads()` hands torch all
four cores on a box its own docstring says it must not starve.
[ops-14-model-jobs-on-the-event-loop-and-torch-takes-all-four-cores]**

`grep 'to_thread|run_in_executor' backend/spielplan` returns only `backup/nightly.py:186-187`.
`worker.py:117-140`'s `_ledger_map_refit` awaits `refit.refit_all(...)` directly and `:239-252`'s
`_placement_reconciliation` awaits `reconcile.reconcile(...)` directly. `placement/tower.py:99-102`
reads: "§2's reference box is 4 vCPU, and the box also runs Postgres, the API and the worker.
Letting torch claim every core makes the nightly sweep starve the request path" — followed by
`return max(1, min(4, os.cpu_count() or 1))`, which on the reference box is every core.

**16. The worker's migration wait blames the backend for anything, and leaks its pool.
[dd-deploy-worker-wait-exhaustion-message-and-pool]**

`worker.py:320` opens the pool before the `for/else` at `:325-339`, whose `raise` happens outside
the `try/finally` at `:362-369` that closes it — so `pool._pool` is still open after `main()`
raises, and with `restart: unless-stopped` the worker re-opens one every ~60 s. The message ("is
the backend running?") is wrong for a renamed migration the backend crash-loops on and for a
backend mid-way through a migration longer than 60 s on the corpus database.

**17. Process-local state assumes one uvicorn worker with no guard.
[arch-09-process-local-state-assumes-one-uvicorn-worker-with-no-guard]**

`api/tonight.py:69` (`HUB`), `home/rail.py:140-141` (`_BUFFERS`/`_SEQ`), `push/send.py:88`
(`_IN_FLIGHT`), `scoring/backbone.py:231` and `placement/tower.py:108` (`_CACHE`) are
process-global. Correct for the shipped single-worker CMD (`ops/backend.Dockerfile:61`), enforced
nowhere: a `--workers 2` silently splits the household into two lobbies and two rails. The
repository keeps static guards for exactly this class of compose/Dockerfile invariant and this one
is missing.

### The backup job and the restore

**18. The only documented restore procedure produces an install with no connector config and the
wrong push keypair. [ops-01-restore-runbook-missing-and-wrong-key-restore-500s]**

`docker-compose.yml:33-37` is the sole restore instruction in the repository — a comment reading
`docker compose exec db pg_restore -d ... /backups/<dump>`, with no `--clean --if-exists` and no
instruction to stop the app — and `README.md:52` ("Back up `.env` alongside the nightly
`pg_dump`s") is the whole restore story. Run against a target that has completed §3.1's first
boot, which is what `docker compose up` does before anyone can restore anything, it exits 1 with
333 errors: `connector_config`'s COPY fails on the foreign key to `data_encryption_key` and the
table ends with 0 rows, `app_setting`'s COPY fails on the primary key so the VAPID keypair stays
the fresh install's, and `app_user` restores. The result boots, accepts logins, shows Jellyfin as
unconfigured, and every restored `push_subscription` is bound to a public key the server no longer
holds. `get_connector_secrets` (`core/secrets.py:129-130`) returns `{}` rather than raising, so
nothing reports the loss.

**19. Rotation's own-name test is a glob, so an operator's hand-saved dump is deleted.
[dd-deploy-rotation-glob-deletes-operator-copy]**

`backup/nightly.py:86-90`'s `dumps()` selects `spielplan-*.dump` while its docstring and `prune`'s
contract at `:108-110` promise "only files this job's own naming produced". Any file an operator
names the obvious way — `spielplan-2026-08-14-before-upgrade.dump`, the copy the compose comment
tells them to keep next to the rotated ones — matches, and because `-` (0x2D) sorts before `0` it
is the *oldest* of the set and is unlinked next time fifteen candidates exist. The existing test
(`test_backup.py:684-696`) tries only `before-the-upgrade.dump.keep` and `notes.txt`, neither of
which matches the prefix.

**20. An IPv6 `DATABASE_URL` gives a working app and zero backups.
[dd-deploy-ipv6-database-url-breaks-pg-dump]**

`backup/nightly.py:139-146` rebuilds the netloc as `f"{parts.username}@{host}"` from
`urlsplit().hostname`, which returns an IPv6 literal without its brackets, so
`postgresql://u:p@[::1]:5432/db` becomes `postgresql://u@::1:5432/db` and libpq rejects it
("invalid integer value \":1:5432\" for connection option \"port\""). asyncpg parses the bracketed
original fine, so the backend and every other job run normally. `nightly.py:20-22` names "an
install pointing at a Postgres outside this compose file" as a supported case, which is exactly
where an IP literal appears.

**21. A missing `pg_dump` binary leaks a 0-byte `.partial` per attempt, for ever.
[dd-backup-missing-pg-dump-leaks-partials]**

`backup/nightly.py:159-163` opens `<name>.dump.partial` and *then* calls `subprocess.run`; a
`FileNotFoundError` propagates from inside the `with`, so the `partial.unlink` under

## 4. Schema changes

**One new migration is genuinely needed, and it carries exactly two things.**

```sql
-- 00NN_ops.sql — M4.7. §2 (the one DEK row), §6.6 System (backup status), §5.3.

-- sec-10: ensure_dek is SELECT-then-INSERT with no lock; three concurrent first boots produced
-- two active rows. §2 says "the one DEK row", and the rotation and repair executors this
-- milestone adds both assume exactly one.
CREATE UNIQUE INDEX data_encryption_key_one_active
    ON data_encryption_key ((true)) WHERE retired_at IS NULL;

-- ops-11: §6.6 System names "job health ... backup status". last_run is an in-process dict and
-- BackupReport is logged and dropped, so a restart cannot know whether last night's dump
-- happened and no surface can say a job failed.
CREATE TABLE job_run (
    id          bigserial PRIMARY KEY,
    name        text NOT NULL,
    started_at  timestamptz NOT NULL DEFAULT now(),
    finished_at timestamptz,
    ok          boolean,
    detail      jsonb
);
CREATE INDEX job_run_name_started ON job_run (name, started_at DESC);
```

Nothing else in this milestone touches the schema. `data-08`'s runner fixes are code
(`db/migrate.py`), and its finding says so explicitly. `data-12`'s `DROPPED_COLUMNS` change is a
Python constant. `sec-10`'s AAD needs no migration — old rows open with the `None` fallback.

**On the number, and the ordering risk.** `backend/migrations/` ends at `0015_seed.sql`, so `0016`
is next free *today*. M4.6 lands before this milestone and will need one of its own (§6.6's
two-role account table and `is_active`), which means this file is almost certainly **`0017_ops.sql`**.
Take the next free number at the moment you write it, and never renumber: `CLAUDE.md`'s rule is
absolute — `backend/migrations/NNNN_*.sql` are sha256-checksummed and a mismatch is a hard startup
error. Two milestones each holding an unmerged `0016` on separate branches is the one collision
this plan cannot prevent, so if M4.6 is still open when this work begins, coordinate the number
before writing the file rather than after.

**Applying it over populated tables is itself a test obligation.** The unique index will fail on
any install that already carries two active DEK rows (`sec-10`'s race). Write the migration so it
says why in a comment, and make the upgrade drill (§6) apply it against a database seeded with two
active rows so the failure is discovered here rather than on the household's box.

## 6. Exit criterion

Run as a drill, on a scratch stack, with the numbers that constitute a pass:

   worker`; `pg_restore --clean --if-exists --no-owner -U spielplan -d spielplan
   /backups/<dump>`; `docker compose start backend worker`.
   **Pass:** `pg_restore` exit 0; `docker compose logs backend` contains `applied migrations` with
   **zero** versions listed, or the boot line saying none were pending — and the line is *visible*,

## 7. What this milestone deliberately does NOT do

- **It does not make the worker's tick concurrent, and it does not move the model jobs off the
  loop.** `ops-04` and `ops-14` both offer that as the fuller fix and both warn it collides with
  the other. What ships is the cheap half: `RETRY_AFTER`, `stage` ordering that already exists,
  duration logging that makes the real-corpus numbers measurable, and `tower_threads` giving the
  request path two cores back. The measurement comes first; the restructure is M4.11's or M5's,
  with numbers rather than argument.
- **It does not cancel a running job on SIGTERM.** `stop_grace_period` buys the time; actual
  cancellation needs `dump()` to hold the `Popen` and every job to be cancellation-safe, which is a
  different change with a different risk profile. `ops-08` says so.
- **It does not build the §6.6 System card in full.** Whatever owner decision 2 chooses, "job
  health, queue depth, last syncs, backup status, logs" is more than three facts, and the rest is
  M5's.
- **It does not add an HTTP rotation route.** §2 makes rotation an operator action;
  `tq3-secrets-rotation-row` and `spec-08` both say a CLI, not a route.
- **It does not amend §2's "the artifact bundle and raw store are already immutable files".**
  `cs-67` shows both halves are false, but amending the spec is the owner's. What ships is the
  runbook telling the truth — the bundle is large, mutable and re-importable, and a restore onto a
  box that lost `/data/artifacts` must re-import — and a note that "and raw store" has no writer
  until M5. The clause itself goes to the owner with the rest of the spec-v2.2 batch.
- **It does not add an admin route that re-stages the active bundle version from disk.** `cs-67`
  names it as the prerequisite for a complete restore story. It is a Data-tab route and belongs
  next to the import wizard, not in this milestone.
- **It does not add `uv.lock`.** `dd28` explicitly says not in the same change unless the owner
  takes the whole supply-chain finding.
- **It does not touch the read-then-write / advisory-lock theme** (the Rank seal, the Tonight join
  race, the connector `user_tokens` lost update). Those share a root cause with nothing here and
  belong to their own milestone; `data-08`'s advisory lock is in scope only because it is the
  migration runner, which is boot.
- **Where the deferred work went:** the account-creation half of the drill is M4.6's; the Tonight
  lifecycle is M4.8's/M4.9's; the 409 seam is consumed by M4.10 and M4.12; the job-registry
  timeout and `job_run` row are consumed by M4.11, M4.13 and M4.14; §6.6's System card and the
  admin re-stage route are M5's.

## 8. Risks and gotchas

**The migration number is a live collision.** `0016` is next free today; M4.6 will almost certainly
take it. Take the next free number when you write the file, never renumber, and never edit an
applied migration — `CLAUDE.md`'s Gotchas make a checksum mismatch a hard startup error, and
`data-08` reproduced exactly what a renamed migration does (a `DuplicateTableError` at boot plus an
orphaned `schema_migration` row that no tooling reports). This milestone's own orphan detection is
what makes that visible in future.

**The unique index can fail on a real install.** `data_encryption_key_one_active` is exactly the
constraint `sec-10` says the code violates under concurrent first boots. If any install carries two
active rows, the migration aborts at boot. Write the comment that says so, make the upgrade drill
exercise it, and give `spielplan-secrets reset` the ability to retire the loser — otherwise the
first thing this milestone does on a real box is refuse to start.

**The `USER` directive breaks bind mounts silently.** `./data/*` on the host is owned by whoever
created it. After the Dockerfile switches to uid 1000, the worker cannot write `/data/backups` and
the importer cannot write `/data/artifacts` unless the host directories are chowned. README needs
the line, and so does `.github/workflows/ci.yml` — the GitHub runner user is not uid 1000, and
`ci.yml:116-125` creates `data/import` before the stack comes up. A green local run proves nothing
here; check the CI e2e job.

**Deleting `insecure-dev-secret` breaks the whole integration layer if `conftest.py` is not fixed
in the same commit.** `spec-04` states it as a "do not": that fallback is what lets 1100+ backend
tests construct `Settings`. The validator, the three deletions and the conftest fixture are one
commit.

**`e2e/run.mjs`'s readiness loop must be re-checked after the 503 change.** It is a wait-until-
success loop, so a 503 during startup is the correct "not ready yet" — but confirm it, and confirm
`ci.yml:131-139`'s `curl -fsS` loop, before assuming. Also confirm the image HEALTHCHECK's
`--start-period=20s --retries=5` still lets a cold stack come up.

**Do not run `e2e/reset.mjs` casually.** It drops the database and wipes `data/artifacts`. And
plain `playwright test` against a used stack makes the first-boot and bundle specs skip and
fake-pass; `run.mjs`'s two phases plus the backend restart are load-bearing.

**The integration layer skips silently without `TEST_DATABASE_URL`,** and the PGlite schema tests
skip without `backend/tests/pglite/node_modules`. Half this milestone's assertions live in those
two layers, so a green no-DB run is not evidence. Bring the database up with
`docker compose -f docker-compose.yml -f ops/compose.dev.yml up -d db` — the overlay is never
auto-loaded, pass both `-f`.

**`pytest` from the repo root without a path argument errors on every async test:** the config with
`asyncio_mode=auto` lives in `backend/pyproject.toml`. Always
`backend/.venv/Scripts/python -m pytest backend/tests -q`.

**`ruff check .` from the repo root, not from `backend/`** — the root `ruff.toml` widens scope to
`ops/`, which this milestone edits (`ops/devstub.py`, `ops/backend.Dockerfile`). Line length 108 is
deliberate; do not reformat wholesale, and do not run `ruff format` over untouched code.

**Keep every log line, error message and test output ASCII.** Windows cp1252 consoles crash on
decorative glyphs, and this milestone writes more log lines than any other.

**Diffs are surgical.** Every changed line must trace to a finding above (or, for the one 409
handler, to the explicitly-flagged seam). No speculative abstraction: `dd-health-probes` offers an
`acquire(timeout=...)` parameter on `pool.acquire()` "so request routes can opt in later" and calls
it a separate decision — do not take it. `ds07` deletes a knob rather than documenting one for the
same reason.

**Two findings will re-emerge if the tests are written loosely.** `dd03`'s degradation is only real
if the test drives the *routes*, not `load_jellyfin` — the previous row proved a property with a
bare asyncpg connection and shipped both failure modes past it. And every static guard added here
needs a self-test that feeds it a synthetic violation, because `ddocs-08` and
`tq3-one-published-port` are two guards that passed on a compose file of pure comments. A guard
without a self-test is the exact instrument this milestone is repairing.
