# M4.11 — Jellyfin sync, connectors and push: make seen states flow both ways, and make the prompt arm once

> ## DECISIONS TAKEN SINCE THIS PLAN WAS WRITTEN
>
> This plan was drafted while the questions below were still open, so it may present two branches or defer to "an owner decision". **It no longer does.** The rulings are binding; where the plan below offers a choice this section has already made, follow this section. Full reasoning and evidence are in [`ROADMAP-to-M5.md`](ROADMAP-to-M5.md#decisions-taken).
>
> **Decision 172 — May the sweep adopt Jellyfin's Played as seen, close an armed prompt as answered, push a series unseen, and let a recomputed Series.Played override an explicit seen?**  
> Four answers. (1) Adoption stays: an absent `user_title` row is a default, not an assertion, and Jellyfin history is real history. (2) The sweep may NOT close an armed prompt — but the fix is that it must not *adopt* for a title whose prompt is open, not that it labels the closure differently. Drop `closed_by_sync` and migration 0020's share of it entirely; while a finish prompt for a (user, title) is open the sweep leaves that row alone, and only a tap closes the prompt. For that to mean anything, "no" must become state: the declining tap writes `unseen` as an explicit action. (3) An app-side `unseen` on a `kind='series'` title is NEVER written to Jellyfin — it is app-only, `jf_synced_at` is stamped so the sweep does not re-owe it, and the surface says so. (4) A computed `Series.Played` may mark but never un-mark: the sweep adopts Jellyfin-played over an app `unseen` or an absent row, and never adopts Jellyfin-not-played over an app `seen`.
>

**This milestone is not in §12 either.** §12's M1 row — *"Jellyfin connector + user linking +
seen-state two-way sync … | seen states flow both ways for both users"* — was closed against a
one-user, one-copy, movie-only fixture. Against a real library the sweep aborts permanently on a
tokenless link, reverts an explicit "not seen" whenever a duplicate copy is Played, un-marks a
series the day its next season lands, never falsifies ownership, promotes a dead token back to
"linked", and never arms a finish prompt for television at all. The push half that M4 added
delivers every notification onto one replacement tag, cannot be enabled on a member's second
device, and re-asks a dismissed question every sixty seconds. This milestone makes the M1 exit
criterion true for the household the spec actually describes: two members, a library with
duplicated copies and a running series, and two phones each.

It is numbered M4.11 rather than folded into M5 for the reason `docs/TESTING.md` already
establishes for M4.5 and M4.6: M0–M4 are shipped rows, and a shipped row that is wrong is
repaired in a milestone of its own so the repair carries its own coverage. It follows M4.10
because the single leak from this territory into the rest of the app — the Jellyfin round trip
inside the verdict transaction — is M4.10's to move, and both milestones would otherwise edit
`rate/session.py`'s push path in the same lines.

## 1. Why these changes are one milestone

`sync/seen.py`, `sync/playback.py`, `connectors/{jellyfin,resolve,registry}.py` and `push/` are
one territory that nothing else in the codebase edits. That would be a weak argument on its own.
The strong one is that **seven of these repairs rewrite the same loop**, `sync_user`'s
`for title_id, (item_id, jf_seen) in collapsed.items():` at `backend/spielplan/sync/seen.py:283`:

| repair | finding | what it does to the loop |
|---|---|---|
| hoist the token check | syncpush-01 | the `break` at `:311` becomes unreachable for a *missing* token |
| stamp `jf_synced_at` conditionally | syncpush-02 | `_push`'s stamp at `:141-144` gains the pushed value |
| the series adopt rule | dd05-series-played-recompute | the adopt branch at `:318` gains a `kind` guard |
| the copy-set, not a pointer | dd17-duplicate-copy, dd17-representative | `_collapse`'s return type changes, and `:242-249` stops writing |
| falsify `is_owned` | cs-11 | needs the sweep-level union the loop currently discards |
| no adoption under an armed prompt | spec-14 | a second guard on the same adopt branch |
| bounded, non-overlapping sweeps | syncpush-07 | resolution leaves the loop entirely |

Those cannot be split across two workstreams: each is a different conditional on the same six
lines, and the `_collapse` return-type change reaches all of them.

The push half is inseparable from the sync half because **the finish prompt is the
notification**. syncpush-04's re-arm, syncpush-10's single tag, fec02's per-device subscription
and fe-lc-15's stale key are four faults in one user story: *the television finishes an episode
and the phone asks about it, once*. Fixing the arming without the tag still means a Tonight
invitation silently replaces the question; fixing the tag without fec02 means only one phone per
member ever sees it.

Two things this milestone deliberately keeps out of scope live in §8 below.

## 2. What is broken today

Every line number is against `50753a3` plus the uncommitted spec amendments; each was re-read in
the worktree. Findings are grouped where one repair answers two.

### Link state and the sweep's own arithmetic

**1. A link without a per-user token stops that member's whole sweep at the first owed row,
permanently.** [`syncpush-01`]
`sync/seen.py:126-130` — `if not user.token: await _mark_needs_relink(...); return False, "no per-user Jellyfin token — re-link required"`.
`sync/seen.py:306-311` — `elif refusal and "re-link" in refusal: … completed = False; break`, whose
comment justifies the `break` for a *dead* token. A *missing* token takes the same branch.
`api/admin.py:143-151` creates that state on purpose ("A link with no token is real but incomplete:
it attributes playback and feeds the P(seen) prior"). So from the first title such a member marks
in the app — which leaves `jf_synced_at` NULL, i.e. owed — every later sweep aborts on that row:
nothing after it in `/Items` order is adopted, `completed` never lists the user, and a redundant
`needs_relink` UPDATE is re-issued every fifteen minutes. Nothing can ever settle the row, because
the only thing that would is the write the missing token cannot make.
*Should:* a tokenless link runs the loop in **adopt-only** mode. The check is hoisted out of the
loop, `needs_relink` is marked once, rows stay owed, and a later sign-in settles them. The `break`
stays only for `exc.is_auth_failure`, where hammering the server is the real concern. It must not
fall back to the admin key (§7.3, §14 risk 3) and must not skip tokenless users, which would drop
the P(seen) prior the link exists for.

**2. `needs_relink` is cleared by any sweep that had nothing to push, and an origin change leaves
everyone reading "linked" with no token.** [`dd17-dead-token-promoted-to-linked-by-quiet-sweep`,
`dd17-origin-change-drops-tokens-but-leaves-users-linked`]
`sync/seen.py:370-377` promotes on `user.token and user.name in report.completed`, under a comment
that claims the opposite ("Clear a stale re-link flag only on positive evidence"). But a sweep only
sends the token for rows with `jf_synced_at IS NULL` (`:300`), so a quiet sweep exercises the token
never and promotes a revoked one on no evidence. `test_a_clean_sync_clears_a_stale_re_link_flag`
(`backend/tests/test_seen_sync.py:323-334`) pins exactly that weak evidence. Separately,
`connectors/registry.py:171-185` correctly drops `api_key` and `user_tokens` when the origin
changes (§14.3) but writes nothing to `app_user`, so every account stays `'linked'` with no token —
which by finding 1 is the state that then freezes the sweep at their next tap.
*Should:* promotion requires evidence of a **successful write** — a new `wrote: set[str]` on
`SyncReport`, set where `_push` returns True. And `save_jellyfin`, when `moved` and tokens were
held, sets every linked account to `needs_relink` in the same statement sequence, citing §14.3 +
§7.3.

**3. Any non-401 Played-write failure reads exactly like a healthy sweep — and promotes the failing
link.** [`cs-05`]
`sync/seen.py:130-139` logs one warning and returns `(False, reason)`; `sync_user` `continue`s at
`:312`, so `completed` stays True and `SyncReport` gains nothing — it has **no failed-push counter
at all** (`:58-85`). A 404 (a server below the pinned 10.9 has no `/UserPlayedItems`), a 500, a
proxy that drops DELETE, a timeout: the whole app→Jellyfin direction can be dead for the life of
the install while the admin card prints `pushed 0 · adopted 0 · unchanged N` and `sync_all:370-377`
restores a previously-flagged link to healthy.
*Should:* `push_failed: int` and `push_errors: list[str]` on `SyncReport`, incremented in the
non-auth branch; `sync_user` returns `completed=False` when any push failed; the log line rises to
`error`; the counter renders beside pushed/adopted/unchanged at
`frontend/src/routes/admin/connectors/+page.svelte:192-197`. Do **not** widen
`JellyfinError.is_auth_failure` to cover 404 — a missing route is not a credential problem, and a
re-link prompt sends the person to type a password that cannot help.

**4. Two concurrent actions leave app and Jellyfin disagreeing, and the next sweep reverts the
person.** [`syncpush-02`]
`set_state` commits the app row (`:167-175`, autocommit) and then awaits the network (`:189-191`)
with no ordering between the two, while `_push` stamps `jf_synced_at = now()` **unconditionally**
on success (`:141-144`) without checking the row still holds the value that was pushed. Two phones,
or one impatient double tap, can leave the DB on the later value and Jellyfin on the earlier one,
both stamped as agreed; the reconciliation table then reads "present + stamped + disagrees" as a
Jellyfin-side change and adopts it (`:314-319`), reverting the explicit action §7.3 says outranks
Jellyfin's inferred state — and stamping a fresh `state_changed_at`, so the correction is
unrecoverable from the row.
*Should:* the write order and the push order must be the same order. See §4 step 4a — and note in
§9 that the finding's published two-line conditional stamp **does not on its own fix the
reproduced race**.

### Duplicate copies

**5. The representative pointer follows whichever copy the current user played, so it flips every
sweep — and every duplicated title is rewritten two or three times per user per sweep.**
[`dd17-representative-pointer-flips-per-user-sweep-and-loses-finish-prompt`,
`dd17-duplicate-copies-defeat-upsert-churn-guard-and-inflate-relinked`]
`sync/seen.py:242-249` writes `title.jellyfin_id` to the copy *this user* played, once per user
sweep, and `sync_all:357` runs users in id order — measured pointer sequence across three sweeps
with two users on different copies: `jf-1, jf-1b, jf-1, jf-1b, jf-1, jf-1b`. `playback.observe`
resolves `NowPlayingItem.Id` only against `title.jellyfin_id` (`sync/playback.py:127-132`), so a
session on any other copy is `unresolved` and never arms §7.3's prompt — permanently for the
first-listed member, since the order is fixed. Upstream, `connectors/resolve.py:157-161` counts
every second live copy as `relinked` and `:181-186`'s churn guard is true for every copy but the
current pointer, so the "~11,000 dead row versions" arithmetic that guard was written for
(`resolve.py:175-180`) is silently re-opened for exactly the duplicated titles; and
`sync/seen.py:330` overwrites `report.resolve` per user, so "sync now" shows only the last user's
figures.
*Should:* the pointer is decided once per sweep, deterministically, and never by a Played flag;
`relinked` counts only a genuine re-link (the old id is absent from the library); `report.resolve`
is a sweep-level fact because resolution is.

**6. An explicit "not seen" is reverted by the next sweep whenever a non-representative copy is
Played.** [`dd17-duplicate-copy-explicit-unseen-reverted-by-next-sweep`]
`set_state` pushes DELETE to `title.jellyfin_id` only (`seen.py:178`, `:189-191`) and stamps; the
other copy keeps `Played=true`; the next sweep OR-collapses (`:239-240`), sees "present, stamped,
disagrees" and adopts. Reproduced both with two users on different copies and with one user who had
played both. This is §7.3's "App is authoritative for explicit user actions" failing on the exact
library `_collapse`'s own docstring is written for — *"Movies" and "Movies 4K"*.
*Should:* "unseen" clears **every** copy of that title. It must not be fixed by dropping the
OR-collapse (that re-opens `test_a_duplicate_copy_cannot_erase_an_explicit_seen`) nor by ceasing to
stamp `jf_synced_at`.

### Series

**7. "Not seen" on a series issues DELETE against the Series folder, which Jellyfin executes as a
recursive MarkUnplayed — and undo writes `Played=false` over history the app never owned.**
[`dd05-series-unseen-is-a-recursive-mark-unplayed-on-jellyfin`, `data-10`]
`seen.py:178` fetches `jellyfin_id` and never `kind`; `ITEM_TYPES = "Movie,Series"`
(`connectors/jellyfin.py:34`) means that id is the Series folder item;
`connectors/jellyfin.py:276-281` sends `DELETE /UserPlayedItems/{item_id}`. Jellyfin's
`Folder.MarkUnplayed` iterates every recursive non-folder child and resets `Played`, `PlayCount`,
`PlaybackPositionTicks` and `LastPlayedDate` on each. §6.1's not-seen correction in Rate, the title
card's unseen control and `rate/session.py:627-664`'s `_compensate_push` all reach it. The reverse
is MarkPlayed on every episode with `PlayCount++`. `_compensate_push` compounds it:
`played = prior.existed and prior.state == "seen"` (`rate/session.py:651`) means undoing a verdict
on a title that had **no row at all** writes an explicit `Played=false` — the one row `seen.py:26-28`
says never happens ("push the app's absence over Jellyfin's history") — and for a series that is
the recursive wipe.
*Should:* a `kind` guard in both writers, and `_compensate_push` returns before the token lookup
when `not prior.existed`. The mapping change needs an owner decision (§3, decision **S1**). It must
not be solved by pushing to individual episodes: the app has no episode identity (§4.1 rule 5).

**8. A new season flips Jellyfin's computed `Series.Played` to false and the sweep adopts it over
the household's explicit "seen".** [`dd05-series-played-recompute-adopted-over-explicit-seen`]
Jellyfin does not store Played on a Series; `Folder.FillUserDataDtoValues` computes
`dto.Played = playedCount >= totalCount`, and `= true` when `totalCount == 0`. So the flag changes
with no person acting — when episodes are added, or when an empty series folder is scanned — and
`seen.py:314-319` treats "stamped, disagrees" as a newer human action. An explicit "seen" becomes
"unseen" the day Season 2 lands; an empty stub is adopted as "seen".
*Should:* for `kind='series'`, a computed folder flag is not "inferred state" in §7.3's sense in
the un-marking direction. Owner decision **S1**.

**9. Series playback never arms the finish prompt, and the fake plays a shape a real server never
sends.** [`dd05-episode-sessions-never-arm-the-finish-prompt`, `dd05-fake-and-e2e-play-a-series-item-real-jellyfin-never-emits`]
`connectors/jellyfin.py:224-243` drops `NowPlayingItem.Type` and `SeriesId`; `observe` resolves the
*episode's own* Id against `title.jellyfin_id`, which for `kind='series'` holds the Series item id
from the `/Items` sweep. Every episode session — including one Jellyfin already marks Played —
lands in `report.unresolved`, which `worker.py:86-88` never logs and no surface shows. Nothing in
the suite can fail, because `ops/fake_jellyfin.py:245-263`'s `force_session` emits the *Series*
item with no `Type` at all, and `e2e/specs/08-jellyfin.spec.js:118-131` plays `jf-6` that way. So
the whole Series partition sits outside §13's capture loop while "rating capture > 70% of finished
playbacks" reads healthy.
*Should:* `NowPlaying` carries `item_type` and `series_id`; `observe` resolves
`series_id or item_id`; the fake emits the documented Episode shape; `report.unresolved` is logged.
What "finish" means for a series is owner decision **S1**.

### The prompt

**10. The 15-minute sweep adopts Jellyfin's Played flag and closes the armed prompt as "answered",
which is the opposite of what coverage row 41 and §7.3:315 say.** [`spec-14`]
`spec_coverage.toml`'s `jellyfin-acquisition-eval-playback-arms-prompt-never-writes` says *"only the
user's explicit tap writes seen"*; `docs/spielplan-spec_v2.1.md:315` says *"Jellyfin playback is a
suggestion, never a silent write"*. `sync/seen.py:290-293` adopts Jellyfin's auto-set Played for a
title with no `user_title` row, and `sync/playback.py:211-224` then closes any open prompt as
`'answered'` — which `test_an_open_prompt_closes_when_the_state_arrives_another_way`
(`test_playback_prompt.py:343-354`) pins as correct. For a linked member the prompt window is at
most one sweep, "offers the verdict flow" never happens, and §13's denominator counts sync-closure
as an answer.
*Should:* owner decision **S2** — either a distinct `closed_by_sync` state, or no adoption while a
prompt is open. Row 41's `what` is reworded either way; a row whose own test asserts its negation is
the defect.

**11. Answering "No" re-arms the prompt on the next minute's poll, with a fresh push each time.**
[`syncpush-04`]
`answer`'s docstring states the rule — *"Both answers close the prompt: 'no' is an answer, and a card
that comes back after being dismissed teaches people to ignore the banner"* — and nothing enforces
it. The guard is the partial unique index on `prompt_state IN ('armed','shown')`
(`0006_jellyfin.sql:39-41`) plus `arm`'s refusal for a title already `seen` (`playback.py:80-85`); a
dismissal produces neither. The film is still above the threshold, the poll runs every sixty
seconds, and every successful `arm` calls `notify` (`:133-141`). Measured: `answer(finished=False)`
then three polls gives rows `[(1,'dismissed'), (2,'armed')]` and two pushes.
*Should:* the dismissal is part of the guard, keyed on **the viewing** — which is what
`jf_session_id` was recorded for, per `0006_jellyfin.sql:29-37`'s own comment. Do not widen the
index predicate to include `'dismissed'`: that same comment explains it would suppress the
legitimate rewatch three months later on the same television.

**12. `answer` consumes the prompt before it writes the state, so a failure between the two loses
both.** [`syncpush-16`]
`playback.py:265-268` marks the event answered/dismissed; `:270-279` then calls `load_jellyfin`
(which can raise) and `seen.set_state`. The connection is autocommit. Probe: `set_state`
monkeypatched to raise leaves `prompt_state='answered'` and **no** `user_title` row, and nothing
re-arms it — `observe` only arms while a live session is above the threshold, which by then it is
not. Each occurrence silently subtracts from §13's numerator.
*Should:* the state write is the durable half and goes first; `pending()`'s auto-close makes the
window between the two self-healing. The two writes plus the network push must **not** be wrapped
in one transaction — that reintroduces the fault M4.10 is removing.

**13. The prompt's tap sets seen and then offers nothing — not §7.3's verdict flow, and not even the
banner refresh the code cites as its substitute.** [`cs-38`]
`frontend/src/lib/components/FinishPrompt.svelte:29-45` posts and filters its local queue: no route
to §6.1's queue, no inline verdict control, no callback prop, and `api/state.py:80-92` names no next
step. The omission is justified in a comment by proposal 150, which no owner decision adopts, and
even proposal 150's own substitute is undelivered: it says the answered title *"leaves a title in
the banner's population"*, the banner is server-rendered from `/api/home`, and `<FinishPrompt />` is
mounted with no props (`frontend/src/routes/+page.svelte:256`) while the identical seen write from
the title card **does** call `loadShelves()` and says why (`+page.svelte:219-228`).
*Should:* an `onAnswered` prop wired to `loadShelves()`, plus §7.3's verdict affordance. Owner
decision **S3** on which affordance.

### Ownership, resolution and the connector

**14. Ownership only ever becomes true.** [`cs-11`]
`connectors/resolve.py:163-173` writes `is_owned = true` for every item the sweep sees, and no code
path anywhere writes false — `grep is_owned` over `backend/spielplan` finds that one write and the
importer's default. `sync_user` already builds `collapsed`, the complete set of title ids the
library holds, and uses it only for `owed_unreachable` (`:325-329`). A title deleted from Jellyfin
keeps `is_owned`, stays in §6.2's candidate pool (`tonight/pool.py:231`) and on the owned Home
shelves (`home/shelves.py:758/814/857`), and its winner card deep-links to an item id the server no
longer has. §7.2 requires the opposite in as many words: *"mark removed titles `is_owned = false`
… re-derived from Jellyfin, never trusted stale"*. `test_ownership_is_re_derived_not_trusted_stale`
asserts only the false→true direction.

**15. The name/year fallback attaches an item to an arbitrary same-named title and calls it a
match.** [`cs-04`]
`connectors/resolve.py:115-134` adds a fourth key §7.1 does not name, resolved by
`ORDER BY t.id LIMIT 1` with the year applied only when Jellyfin supplied `ProductionYear`
(`($3::int IS NULL OR t.year = $3)`). No ambiguity check: a name matching five rows silently takes
the lowest id, and `upsert_item` then writes `is_owned`, `owned_checked_at` and `jellyfin_id` onto
that row and counts it in `report.matched`. On the real corpus 2,438 titles share
`(kind, lower(name))` and 573 groups collide on kind+name+year. The module's own docstring calls
this *"the only one that can be wrong"* and then does not guard it.

**16. The 10.9 pin is a sentence in a manual test button.** [`cs-39`]
`connectors/jellyfin.py:36-37,169-182` declare `MIN_SERVER_VERSION` and compute `supported`, but the
only caller is `api/admin.py:74-81`'s test button, which returns it to the browser and discards it;
there is no version column in `connector_config`, and neither `save_jellyfin`, `sync_all`, `poll`,
`set_state` nor `make_client` consults it. The one piece of user-facing copy
(`admin/connectors/+page.svelte:180-186`) says *"below the pinned 10.9 — reads may miss fields"*,
while by the module's own comment the 10.9-only route is `/UserPlayedItems`: **reads degrade, the
write does not exist**. With finding 3 that is a 10.8 install passing every visible check while the
app→Jellyfin direction 404s for ever.

**17. `all_items` pages forever, and the worker that runs it is strictly serial with no per-job
timeout.** [`syncpush-08`, `syncpush-07`]
`connectors/jellyfin.py:216-222` is `while True` whose only exit is a short page; it ignores the
`TotalRecordCount` the response already carries (`:211` asks for it, `:214` throws it away) and has
no page cap. Probe: a transport that ignores `StartIndex` fetched 41 pages / 20,500 dicts before the
harness aborted it. `worker.py:307-314` awaits each due job in turn with no `asyncio.wait_for`, so
one wedged sweep takes the entire worker offline permanently and invisibly — no prompts, no refit,
no fold-in, no backup, process alive. Separately, `sync_user` re-runs the full resolver per user
although resolution is user-independent (`seen.py:277-288` → `resolve.py:145-189`, 1–4 queries plus
a fetchrow plus a guarded UPDATE **per item per user**); measured 5.26 s for a warm pass over 1,500
unchanged titles against a zero-latency transport, extrapolating to ~77 s per cycle at the
docstring's own ~11,000 items across two users — during which the 60-second `/Sessions` poll cannot
run. And nothing locks the 15-minute job against `api/admin.py:184-188`'s "sync now".

**18. With Jellyfin unreachable the poll logs a warning a minute, for ever, and no surface says
so.** [`ops-15`]
`sync/playback.py:196-199` and `sync/seen.py:362-364` both `log.warning` and return; the poll runs
every 60 s with a 15 s timeout (`jellyfin.py:98`). A box powered off overnight produces ~480 lines
by morning, 1,440 a day, interleaved with the backup and refit reports the operator actually wants.
The behaviour is correct (§3.3); the observability is not — there is no "unreachable since" state
anywhere, and §6.6's System card promises "last syncs".

**19. Two concurrent links lose a token, because the sealed `user_tokens` map is read-modify-written
with no lock.** [`as05`, `syncpush-05`]
`api/admin.py:158-162` does `cfg = await load_jellyfin(conn); tokens = dict(cfg.user_tokens);
tokens[str(user_id)] = token; await save_jellyfin(conn, user_tokens=tokens)` on an autocommit
connection, and `registry.save_jellyfin:165` re-reads and merges again, so the window exists twice.
`seen.forget_token:388-394` has the same shape, inside `unlink`'s transaction — which does not lock
the row it read. Reproduced against the in-process fake: both link responses said
`has_token=true/linked`, then `/api/admin/users` showed jenny linked with
`has_jellyfin_token=false` and `linked_users=1`. And an account that reads "linked" with no token is
precisely finding 1's permanent sweep stop.

**20. `JellyfinClient` and `JellyfinConfig` print the admin key and every per-user token in their
default repr.** [`sec-15`]
`connectors/jellyfin.py:94-99` marks only `transport` as `repr=False`; `connectors/registry.py:33-43`
holds `api_key` and `user_tokens` at default repr — unlike `push/keys.py:50-61`, which the codebase
already knows to write as `field(repr=False)` ("no accessor and no repr"). Not hypothetical: this
review observed a pytest failure header rendering
`JellyfinClient(base_url='http://jellyfin.test', api_key='fake-admin-key', timeout=15.0)`. §14.3
calls that key admin-equivalent on the whole media server.

### Push

**21. A member's second device can never enable notifications, the off switch lies, a subscription
minted under a dead VAPID key is never rechecked, and the prune cannot reach a row that never
delivered.** [`fec02`, `fe-lc-15`, `syncpush-09`]
`Onboarding.svelte:57-65` derives `pushState` from `devices.length > 0`, where `devices` is
`GET /api/push/state`'s `subscriptions` — whose own docstring says *"This member's devices. Never
the household's"* (`api/push.py:88-89`), i.e. all of that member's devices, not this one. On a second
device the section titled "This device" renders *"Notifications are on for this device"*, lists the
**other** device, and shows only the disable control; the enable button — the only thing that runs
`Notification.requestPermission()` inside a gesture — sits in the unreachable `else` branch
(`:265-277`). Pressing off calls `disablePush()`, which returns `null` because this browser holds no
`PushSubscription` (`push.js:222-232`) so no DELETE is sent, and the component then does

## 9. Risks and gotchas

**The published mitigation for syncpush-02 is insufficient, and the plan corrects it.** The finding
proposes a conditional `jf_synced_at` stamp as a two-line fix. It is worth having (step 2a) but it
does **not** fix the reproduced race on its own: with two pushes in flight, the loser's stamp
correctly fails to match — and the winner's already succeeded, so the row still reads
"stamped + Jellyfin disagrees" and the next sweep still adopts. The divergence is an *ordering*
problem between two writers, and only serialising the read-write-push per (user, title) fixes it.
That is why this milestone depends on M4.6's advisory-lock idiom and why the lock must be the
session-level variant.

**A session-level advisory lock on a pooled connection is a leak waiting to happen.**
`pg_advisory_lock` outlives the transaction and travels with the connection back into the pool.
Release in `finally`, always; set `lock_timeout`; and never hold it across more than the one push.

**Never edit an applied migration.** `0006_jellyfin.sql` and `0005_ledger.sql` are sha256-checksummed
and a mismatch is a hard startup error. The `prompt_state` CHECK is changed by DROP + ADD in a new
file (§5).

**Renaming or deleting a registered test breaks the build.** `test_spec_coverage.py` fails when a
named test no longer exists. `test_a_clean_sync_clears_a_stale_re_link_flag` and
`test_an_open_prompt_closes_when_the_state_arrives_another_way` both change meaning here: rewrite
their bodies in place where the name still describes what they assert, and where it does not (option
B for the latter), rename **and** edit the coverage row in the same commit.

**Making the fake honest turns green tests red before the fix lands.** Step 3b is the contract
