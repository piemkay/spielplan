>

**This milestone is not in §12.** It exists because the numeric stack under `ledger/`,
`scoring/` and `placement/` computes fits without recording the basis they were computed in,
and because three separate readings of "the basis" — the bundle version, the tier-set size K,
and the coordinate a title is actually served at — are each wrong in a way the other two
cannot see. `ArtifactStore.assert_matches`, the one enforcement point §10's invariant names,
has no production caller and its own module docstring says it does. A fit is therefore a
number with no provenance, and every guard that would have caught this is either uncalled, or
green against a fixture whose shape the corpus does not have.

**Thesis: make a fit know the basis it was computed in.** Thread the bundle version instead of
reading the active row, call the §10 invariant at the entrypoints its docstring already claims,
widen "basis" from *bundle* to *bundle + K + coordinate*, and stop the cold half of §5.1's
blend from dominating the warm half by five hundred to one.

Depends on **M4.8** (the corpus-shaped fixture — without it the cold-mask and gate-blend
assertions run on titles `make_bundle.py` cannot express) and **M4.10** (perf-03 must already
have taken the full refit off the tap path, because ml01's invalidation and dd22's incremental
fix both act on the cache-miss branch M4.10 reshapes).

## 1. Why these changes are one milestone

Three arguments, and they are the same argument at three scales.

**The stack is one numeric object and no surface milestone edits it.** `ledger/`, `scoring/`
and `placement/` are the only packages that compute a coordinate, fit a vector, or write a
tier. Nothing in M4.6's Users screen, M5's acquisition pipeline or M6's Map touches them. If
this work is split across milestones, two of them contend for the same four functions —
`observations.standard_embeddings`, `refit.load_cache`, `refit.refit_user`,
`backbone.coordinate` — and the second one to land rebases onto a file it did not read.

**The version-threading theme lives almost entirely inside it.** The review editor's fifth
root-cause grouping is *"the bundle version is inferred from the DB active row instead of
threaded from the caller, and §10's invariant has no caller"*, and four of its five findings
are here (data-01, arch-03, data-03, ml01; the fifth, spec-03, is the docs-side twin of tq1).
One keyword argument on `standard_embeddings`, one on `refit_user`, and three call sites for
`assert_matches` close all of them together. Split them and you get three half-threaded call
graphs, each of which still falls through to `b.state = 'active'` somewhere.

**Widening "basis" from bundle to the full triple pulls in the rest.** A fit is wrong if the
bundle changed (data-01), if K changed (ml01, dd06), or if the coordinate it was fitted against
is not the coordinate it is served at (dd02, cs-01, cs-02). `load_cache` today checks
`hp_digest` and `bundle_version` and nothing else — the same function gains K, and the same
`standard_embeddings` that gains the version also gains the gate blend. dd06's `rescale_level`
helper makes dd06-clamp free by construction: three clamps become one call site each of one
function.

**The schema-hygiene trio rides here because migration numbers are a serialised resource.**
data-06's cascade fix, the three CHECKs weaker than their names, the NULL-permissive cutpoints
constraint and the composite kind FK are all DDL against tables this milestone already owns —
`verdict`, `duel`, `tier_edit`, `ledger_cutpoints`, `ledger_state`, `user_score`. They need one
migration. dd06 needs a column on `tier_edit` in the same migration. Putting the schema trio
anywhere else forces another milestone to negotiate for a number against this one.

**And dd20's numpy-only AST guard lands as written**, now that arch-12's solver split is
deferred: the guarded set is exactly `ledger/model.py`, and it will not have to be widened
mid-milestone.

### β means the opposite of what measured it

## 9. Risks and gotchas

**Never edit an applied migration.** `0001`–`0015` are sha256-checksummed and a mismatch is a hard
startup error. Every DDL statement in §5 is a `DROP CONSTRAINT` / `ADD CONSTRAINT` in a **new**
numbered file. `0015_seed.sql:141-142` is the pattern to copy.

**Constraint names are guesses until you look.** Postgres names an inline FK
`<table>_<column>_fkey`, but `0005` and `0013` declare them inline in ways worth checking. Run
`\d verdict`, `\d duel`, `\d session_answer` (etc.) against a migrated database and write the
real names into the migration. A wrong `DROP CONSTRAINT` fails the whole migration at startup.

**Take the migration number at the moment you write it.** `0016` is free at head `50753a3` and is
what six findings each independently claim. If another pre-release milestone merges first, this
one renumbers. The β migration must be numbered after the structural one.

**A CHECK the nightly job can violate is the 0009 incident.** `0009_scoring.sql:56-65` records it
in full: an uncast `0.8` resolves through float8 where `float4(0.8)` is `0.800000011920929`, so
the ceiling rejected the one value §5.1 measured and a nightly fold-in failed its INSERT inside a
background job. Cast every literal in the β migration, and put the measured band in the code
clamp, not the constraint.

**`ledger/model.py` is numpy-only by contract** — no DB, no clock, no torch. Step 28's freshness
stamps and step 15's `rescale_level` both belong in `observations.py`/`refit.py`, not in
`model.py`, and phase 6's guard will fail the build if that slips.

**`ledger → scoring` is a new import edge.** It is safe — `scoring/backbone.py` imports only
numpy and, under `TYPE_CHECKING`, `models.artifacts`; the only existing `scoring → ledger` edge is
`foldin.py:53`'s `LIVE_LABEL_SQL`, and `backbone.py` is not on that path. Verify it at the seam
rather than assuming: an import cycle here surfaces as a boot failure, not a test failure.

**Test names are contract.** `test_spec_coverage.py` fails the build when a named test no longer
exists, so renaming or deleting a registered test is a build break. Two tests are being changed
here whose expectations invert (`test_scoring.py`'s β tests) — flip the assertions, keep the names.
`test_the_optimum_is_unique_from_any_start` may be deleted **only** because it is confirmed in no
row.

**Two guard tests exist to make this work deliberate, and neither is broken.**
`test_ledger_observations.py:250` asserts that `DELETE FROM verdict` occurs only inside `undo` —
D3's option (b) would move those deletes and must update the guard rather than route around it.
`ops/fake_jellyfin.py` rejecting the admin key on the Played write is intentional and untouched
here.

**Two `is_thin` findings pull in opposite directions if read carelessly.** cs-21 narrows what
counts as thin; the M4.5 row `data-rules-a-feature-block-that-never-hits-is-not-present` widens it
(a block that hit none of its declared columns *is* thin). Both are right: an unenrichable block is
not thin; a block whose keys all miss the contract is. Keep both facts in `blocks_dropped` /
`blocks_empty` so the report can still name them, and change only the verdict.

**`refit_all`'s widened `except Exception` must not swallow the advisory lock's own failures.**
Step 24 puts the lock inside `refit_user`'s transaction and step 29 widens the outer catch; a
connection that is genuinely unusable must still re-raise
(`asyncpg.PostgresConnectionError`/`InterfaceError`), or one dead connection becomes a night of
silently skipped fits with a full report.

**Integration tests skip silently without `TEST_DATABASE_URL`** (auto-loaded from `.env.test`),
and the PGlite schema tests skip without `backend/tests/pglite/node_modules`. Most of this
milestone's assertions are integration-kind. A green no-DB run has not run them; CI will.
Bring Postgres up with
`docker compose -f docker-compose.yml -f ops/compose.dev.yml up -d db` — overlays are never
auto-loaded, so pass each `-f`.

**Line length 108 and no wholesale reformatting.** Several of the files here quote spec sentences
inline that must not wrap, and `ruff format` is informational only. Diffs stay surgical: every
changed line traces to a finding above, comments argue *why* and cite the clause, and commit
bodies carry a `feat(M4.13):`-style prefix with the section or decision number.

**Keep console and test output ASCII.** Windows cp1252 consoles crash on decorative glyphs, and
`ops/m413_exit_criterion.py` is a console script by design.
