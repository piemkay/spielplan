## 0. What changed since v1.1, and why

v1.1 was written before the corpus existed. Since then the corpus project (this repo) built and **measured**:

| v1.1 assumption | Measured reality | Consequence for v2.x |
|---|---|---|
| "No cross-user collaborative filtering" (non-goal) | A 95M-rating collaborative backbone is the strongest single signal. Protocol-matched numbers: on the crowd learning curve the item prior alone holds ρ ≈ 0.44 flat while prior + backbone fold-in grows 0.45 → 0.50 as labels go 5 → 100; at 60 labels on the owned library the ladder reads prior 0.4221 → co-rating 0.5190 → co-rating + content 0.5267 | The crowd model is the core; the app imports its frozen artifacts |
| Aspect vocabulary to be built in 4 passes | Built: 578-term / 11-facet DNA vocabulary, extracted on 2,016 titles (824 owned) with quote-verified evidence, projected on 11,324 | The app imports it; only the incremental single-title extractor ships in-app |
| Mood: 8 axes, 8–13 questions, Bayesian posterior | Sessions are real (ICC 0.17) but the stored profile is worth **0.000** for choose-tonight; **3 shortlist-anchored answers ≈ +0.088 AUC**, and centring on the shortlist matters more than question form; within-evening re-ranking is worth 0.000 | v2.1, as rewritten by the 54a–54h fold: participants answer an **adaptive round** of item-anchored pairs — median about ten pairs (decision 477), hard cap 20, escapable from the sixth — instead of a visible shortlist + question round (owner decision; decisions 175, 214–226). The measured tilt machinery survives underneath — each vote is an item-anchored answer, and the tilt is chosen-minus-rejected DNA centred on the candidate-pool mean; no 8-axis posterior machinery |
| Group: Nash product + fairness ledger | Measured: no aggregation rule dominates plain averaging, and dominance rules cost −0.012. Zero-the-axis-and-surface is an **adopted design** (repair-explanation register), bound by the one measured rule on surfacing: a surfaced split must never ship bare (DNA_MODEL §5.3) | Average scores; zero the contested axis and *tell the group, alternative in hand*; ledger becomes an optional hidden nicety, not core |
| Tiers derived from duels only | The validated Personal Ledger fuses **four** observation arms in one likelihood — 3-class verdicts, margin-weighted duels with ties, explicit tier assignments, rewatch re-ratings — comparisons add within-liked resolution monotonically (+0.008..+0.016) at zero cost to global ranking | Tier list = learned cutpoints on the Ledger latent; drag-and-drop is an observation, not an override |
| Pair-selection heuristics for profile duels | For *profiles*, no selection rule beats random (best +0.0013, CI spans 0); for *ranking*, boundary-targeted selection does help | Random pairs for profile battles; active selection only in the tier-list queue |
| Guests: household-mean taste | Pairs-only guest models stay **below** the bare crowd chart at every tested budget (−0.060 Spearman at 30 pairs, −0.033 at 80; parity ≈ the complete 1,770-pair ordering of a 60-title pool); a 60-title pick-your-favourites grid ≈ 46 pairwise questions for ~10 taps | No stored guest model at all (decision 166): a guest is a session seat carried entirely by that evening's votes. The measurement is now moot rather than acted on — the alternative it argued for, the 60-title grid, goes out of scope with the guest profile itself. |

Two v1.1 principles are **promoted**, not replaced: *"the graph explains itself"* (now backed by the DNA naming layer with evidence quotes) and *"measured beats asserted"* (now the project's operating law, including a documented noise floor: pipeline variance 0.003–0.008 Spearman; anything smaller is a tie).

## 1. System overview

```
┌────────────────────────────── docker-compose ──────────────────────────────┐
│                                                                            │
│  frontend      SvelteKit PWA (static build served by backend or node)      │
│  backend       FastAPI + uvicorn  — REST + WebSocket, auth, scoring        │
│  worker        same codebase, queue consumer — sync, acquisition,          │
│                extraction, nightly refits (CPU-only torch/numpy)           │
│  db            Postgres 16                                                 │
│                                                                            │
│  volumes:  /data/pg  /data/raw  /data/artifacts  /data/cache               │
└────────────────────────────────────────────────────────────────────────────┘
        │ HTTPS via existing Traefik + Cloudflare certs (LAN + Tailscale)
        ▼
  phones (PWA, passkeys)   desktop browser   Home Assistant
```

The backend also serves cover art from its own origin. It fetches each image once, from the household's Jellyfin or from one of the two image hosts §6.8 names, through one polite fetcher it holds for its lifetime, and caches it under `/data/cache`. Every other outbound request, the TMDB lookup for a title with no poster included, is the worker's (decision 485).

**The model, in one paragraph** (full detail: `ARCHITECTURE.md` in the corpus project; §3 and Appendix C vendored as `ARCHITECTURE-extracts.md`). One frozen 64-d collaborative item space (**Backbone**) learned from 95M crowd ratings in the corpus project. A content encoder (**Cold Tower**, torch CPU) places titles *without* ratings into that space from their DNA + metadata — validated: it recovers 67% of the oracle's personal signal on unrated titles. Per person, a **Personal Ledger** holds one latent score per title, fed by four observation arms (verdicts, duels, tier edits, rewatch re-ratings) and refit nightly in seconds by preconditioned optimisation. Ranking = clean item prior + user fold-in over the Backbone, blended β_app≈0.2 — β is the **personal** weight here and the corpus measured the same optimum in the complementary coordinate (§5.1, decision 167). Everything the UI *says* — query predicates, conflict explanations, mood axes, explore frontiers — routes through the DNA vocabulary (the naming layer), never through raw embeddings.

**Hard constraint honoured throughout:** every in-app model update runs on CPU. Measured budgets: Ledger refit for 2 users over 839+ titles — seconds (LBFGS, 64-d); Cold Tower inference — sub-ms/title; nightly jobs — minutes. Backbone (re)training never happens in-app; it stays in the corpus project and arrives as a versioned artifact bundle (§10).

## 2. Deployment

- **docker-compose**, four services as above. `docker compose up` + the setup wizard is the whole install.
- **TLS/ingress:** the app itself serves plain HTTP on one internal port; the operator's existing **Traefik + Cloudflare** terminates TLS. `PUBLIC_URL` (e.g. `https://spielplan.example.tld`) is required config because WebAuthn binds credentials to the origin. The same origin must be reachable via **Tailscale** (already true in the operator's setup) so passkeys work identically at home and remote. Document: changing `PUBLIC_URL` later invalidates registered passkeys.
- **No GPU anywhere.** Torch CPU wheels only. The image must build and run on a GPU-less VM (reference: 4 vCPU, 6–8 GB RAM, 25 GB disk + caches).
- **Configuration:** env vars with sane defaults (`DATABASE_URL`, `PUBLIC_URL`, `SESSION_SECRET`, `SECRETS_KEY`, `TZ`). `SECRETS_KEY` (generated by the setup wizard / compose template) wraps a random 256-bit data-encryption key created at first boot and stored in the DB; connector secrets are AEAD-encrypted under that DEK, each ciphertext carrying a `key_id` for rotation/agility. Rotating `SESSION_SECRET` invalidates sessions only and never touches stored secrets; rotating `SECRETS_KEY` is the **operator command** `spielplan-secrets rewrap` (a declared console script over `core/secrets.py`'s `rewrap_dek`), which re-wraps the one DEK row and leaves every ciphertext and every `key_id` untouched. It is a command and not a UI action because the rewrap needs the **old** key at the same time as the new one, and a running app has no keyboard to type a value it is in the middle of replacing; there is no admin-facing rotation surface (decision 289). The app refuses to start secret-dependent connectors without `SECRETS_KEY` rather than falling back to `SESSION_SECRET`. A web-push VAPID keypair is generated at first boot and stored the same way. Everything connector-related (Jellyfin, LLM, TMDB, OMDb, Trakt) is configured **in the admin UI** and stored in `connector_config` — not env vars, because the owner explicitly wants connector setup in the admin view; env vars may *seed* connector config on first boot for automated installs.
- **Backups:** nightly `pg_dump` to `/data/backups`, rotation 14; the artifact bundle and raw store are already immutable files. Dumps contain ciphertext only — back up the env file (`SECRETS_KEY`) alongside them, or a restored dump cannot decrypt connector config.

## 3. Users, auth, identity

### 3.1 Accounts and roles

Local user accounts, **two roles and no others**: `admin` (full product plus the Admin view) and `member` (full product, no admin — initially Patrick and Jenny; membership is open-ended and a third member is first-class throughout). Roles are assigned by an admin in §6.6 People, and **at least one active admin always exists** — the last one can be neither demoted nor disabled nor deleted (decision 166).

**There is no guest account.** A guest is a Tonight **session seat** on the initiator's phone: no account row, no credential, no profile, no Ledger, nothing that survives the evening. The schema states it rather than trusting it — `session_participant` admits a guest seat only as `user_id NULL` (§4.2, §6.2 step 2).

User creation (§6.6 People): a **one-time password** is issued, the account is locked to a password change at first login, and passkey registration is prompted afterwards. An admin may reissue that one-time password as a password reset, and never sees, sets or types a member's password.

**First boot is a defined sequence, and a bundle-less app is a legal state:** the app boots with `/data/artifacts` and `artifact_bundle` empty, serving the setup wizard and admin routes; artifact-dependent surfaces render an explicit "no movie data yet" state instead of erroring, for an admin with a link to §6.6 Movie data (§6.8, decisions 486 and 527). The wizard runs: create admin → optional env-seeded connector config (§2) → bundle import as the final step (the same importer §6.6 Movie data exposes — that one page is M0 scope), served as soon as the import finishes with no restart (§10, decision 497), **and stops there** (decision 164): member accounts are made in §6.6 People, which is the only place they are made, and which — unlike this wizard — is still reachable on the day the household adds a third member. Member first-run onboarding then walks each phone through PWA install and push permission (§6 preamble).

### 3.2 Authentication — passkeys first

- **Primary: WebAuthn passkeys** (Face ID / Touch ID / Android biometrics) — viable because the Traefik+Cloudflare origin gives real TLS. Registration from the profile page; multiple passkeys per user (phone + desktop).
- **Fallbacks:** password login (argon2) always available; per-device long-lived session cookies after first auth (the v1.1 "appliance" feel — you authenticate rarely); optional 4-digit PIN for fast user-switching on a shared device (decision 165 retires the TV client).
- Sessions: HttpOnly cookies, 90-day sliding; admin routes re-prompt after 24 h. **A password change rotates the session it was made from:** every session for that account is destroyed, the caller's own included, and the response carries a fresh cookie for the device that made the change (decision 208).
- **Shared devices:** **You**, the sheet the avatar opens on every root (§6, decision 527), switches between member profiles, gated by the per-user PIN (You states who is signed in and how, in words — "Member · signs in with a passkey · PIN set for quick switching", a password where there is no passkey and the PIN clause only when one is set; decision 518). Logout clears the session cookie only — passkeys remain registered.

### 3.3 Jellyfin account linking

Admin view maps each app user ↔ one Jellyfin user (`GET /Users`), optional, one-to-one. The link drives: per-user played-state sync (§7.3), playback-event attribution, and the P(seen) prior in rating mode. Authentication is **never** delegated to Jellyfin (v1.1's reasoning stands: the app must work when Jellyfin is down).

### 4.1 Content spine (imported from the corpus bundle, then maintained by the app)

Tables mirror the corpus export (§10 manifest): `title` (canonical key: **`title.id` integer** — adopted verbatim at the one-time seed, because four read paths are id-keyed and two artifacts carry no id vector at all; every later id is Spielplan's, minted at or above 1e9 and below 2^31, and a bundle whose ids reach into that range is refused (decision 162). `imdb_id` is NULL on 21% of titles and must never be the join key), `title_meta` (multi-source, per-source rows kept — "one block = one droppable source"), `title_alias/genre/keyword/country/company/video`, `person`, `credit` (dedupe at read time, never at import), `award`, `platform_rating`, `review` (separate schema or DB — 312 MB with bodies). The bundle's `title_language`, `rating_title_map`, `watchlist` and list registry (its `seed_list` table and `title_list_membership`, not §4.3's onboarding `seed_list.json`) are **shipped, not imported**: nothing in this app reads them (the tower's `lang:` reads `title.original_language`), the import report lists them as skipped, and migration `0039` drops the tables earlier builds filled, `title_list` among them (decision 526). The bundle's MovieLens slice — `ml_genome_score`, `ml_genome_tag`, `ml_link` — **is not imported**: `media-graph-spec_v1.1.md:175` fixes the Tag Genome as a corpus-side validation artifact, "never shipped or imported into the app", and that restriction is **upheld by every import this build performs**: no import this build performs writes those three tables, so §4.3's 983 genome columns are zero for every title it seeds, and the Postgres tables `0003_content.sql` creates stay (decision 291). **One case the sentence deliberately does not cover** (decision 311): an install seeded before decision 291 still holds the 888,023 `ml_genome_score` rows every shipped build up to M4.15 loaded — no migration empties them, decision 162 seeds content once, and `placement/features.py`'s `_genome` still reads them — so there the block is populated. That is correct rather than a defect: those are exactly the cold-masked titles the Cold Tower is asked to place, and giving them the input the tower was fitted over is the better outcome of the two. **What that costs is real and is accepted rather than denied** (decision 304). For the titles §8 acquires it costs nothing — they carry no genome vector at all, by construction. For the corpus's own titles it is not nothing: a fifth of the 5,315 carrying a vector are not warm, which is exactly the set §5.3's sweep hands to the Cold Tower, and nearly all of those carry a cold-masked Backbone row, which §5.1 already treats as no coordinate. Their tower input loses about a third of its non-zero mass, and the Cold Tower's dropout training — which saw all-zero blocks — is why that is survivable rather than a defect. The change is recorded in `title_placement.blocks_imputed` for every title placed off an empty slice — on the pre-291 install above there is no loss to record and that column is correctly empty for exactly those titles — and read by no surface: the genome is one of the blocks `placement/features.py`'s per-block `is_thin` test ignores — a different test from §8.4's thin-facet one (decision 329) — so no badge and no acquisition job follows from it.

**Schema rules imported from measured landmines** (validation in the importer, constraints in the DB):

1. `dna_tag` (extracted, quote-verified; 2,016 titles) and `dna_projected` (inferred; 11,324 titles) are **separate tables, never merged, never unioned**; every read joins carry a `tier` discriminator; 14,181 (title,term) pairs exist in both and must stay distinguishable. `dna_evidence` ships with the extracted tier — a tag without its quote is unfalsifiable.
2. `salience`, `confidence`, `n_sources` are **weights, never filters**. No `WHERE confidence > x` anywhere (a 0.5 cut would delete 44% of the extracted tier; union recalls 93%, intersection 67%).
3. `platform_rating` lives in a **display-only schema** the feature builder cannot import from. Aggregate platform scores are a popularity conduit and are banned as model features (measured: popularity penalty −0.010 Spearman for nothing).
4. `rating_source.id` values (1,2,3,4,7,11,21,23,26,28,31) are **frozen** — they key `fitted_cuts`, `equating_map`, and the dataset arrays. Never renumber.
5. `kind` (movie/series) is non-null, indexed, and **every ranking surface partitions by it** (measured: the unpartitioned crowd top-10 is 8/10 TV series).
6. Postgres PK fixes on import: coalesce NULLable PK components (`title_alias.region` etc.) to `''`; do **not** add UNIQUE constraints on `tmdb_id`/`trakt_id`/slugs (315/171/… duplicate values exist, mostly legitimate movie/series pairs).
7. Deny-list `%_bak%` / `%_good` tables and every stale JSONL in `data/export/` — export reads live tables only (the JSONLs predate the adjudication repairs).
8. UTF-8 everywhere; never "clean" non-ASCII (the corpus legitimately contains CJK, RTL scripts, ZWSP, emoji). Mojibake is repaired by a **conservative heuristic, not a row list**: a review body is re-encoded cp1252 and decoded UTF-8 only when it carries a marker (`Ã`, `â€`, `Â`), the round trip succeeds, the result differs, **and the repair strictly reduces the marker count** — anything that fails a step is left exactly as it arrived, because a legitimately Turkish or Vietnamese review must not be "fixed" into nonsense. Markers seen with nothing repairable are a **warning**, never a silent pass: measured over the shipped `reviews.sqlite`, 86 rows of 485,602 carry a marker and 0 repair, because the damage is a truncated sequence whose lost continuation byte is ambiguous between é/ã/á/à. The fix is upstream, and "fixed individually" was per-row knowledge this repository has never had.

### 4.3 The artifact store (`/data/artifacts/<bundle-version>/`)

Read-only files from the corpus project, loaded at boot **when present** (an empty store is legal — §3.1), hot-swapped on bundle import (§10 swap protocol):

- `backbone.npz` — E, E_full, b_i, μ, plus the per-title support counts `item_n` (the §5.1 gate input) — from `cold_tower_artifacts.npz` + the item stats of the slimmed `content.npz`. E is the **production** basis. Its fitted rows are the corpus's warm-column SVD rows, verbatim. Every row the corpus held out to evaluate the Cold Tower is folded back in as eᵢ = Uᵀrᵢ onto the same user factors, so every crowd-rated title has a coordinate and the tower trained against E stays valid. E is support-weighted (E = V·S). `cold_mask` marks only rows with no crowd rating, and `e_folded` names the folded rows. The method and its held-out measurement travel in `BUNDLE.json`'s `backbone` key (decision 503).
- `cold_tower.pt` — from `data/prep/cold_tower2.pt` (the live model; the earlier `cold_tower` run is superseded — the exporter must ship v2).
- `feature_contract.json` — the definition of the tower's input (per-block `encoding`, `normalise` and `transform` keys are ignored: each cell is the stored value and the meta scalings are fixed; decision 526): the nine content blocks in order with sizes (dna_x 433, dna_p 556, genome 983, genre 179, keyword 3,884, credit 244, country 97, award 2, meta 57 = 6,435 columns), per-column `feature_names`, then the review-text block = columns 0..63 of the 256-d SVD embedding (singular-value order) multiplied by a frozen scalar `text_scale = 1/(max|emb[:, :64]| + ε)` computed over the corpus at export time and stored in this JSON. The contract *references* the review-text SVD components (which ship as their own file) and records all placement-time preprocessing: genome zero-imputation, text truncation + scaling. The genome block is **populated by no import this build performs** — the slice is not imported (§4.1, decision 291) — so zero-imputation is the path those 983 columns take for every title this build seeds. The contract's RULE is unconditional; the PATH is not, and the two are different claims: on an install seeded before decision 291 the three MovieLens tables still hold their rows, `placement/features.py`'s `_genome` still reads them, and the block is populated there (decision 311). §8 stage 9 builds vectors from this file and nothing else.
- `content_X.npz`, `review_text_emb.npz` (+ optional SVD `components` for embedding newly arrived reviews).
- `ledger_hyperparams.json` — the tuned constants of the §5.2 recipe: anchor (ridge) strength λ (currently 3.0), BT weight λ_bt, step count, learning rate, margin-weighting flag + functional form (weights normalised as margin/mean(margin); both are fixed and any other value is refused, decision 526), tie-prior initialisation δ₀ = 0.22 (thereafter fitted), b_i prior τ (or its CV grid; the bundle ships none today, and the app's default is 2.0, decision 509), σ-inflation rate constant and cap. Per-user cutpoints and per-arm sensitivities are **not** shipped — the cutpoints are fitted in-app by design, and **no per-arm sensitivity is fitted either**: the two ordinal arms share one unscaled latent with free cutpoints each, so §3's `a_r` has no term in this model, and a bundle that ships a `sensitivity` key is reported and ignored (decision 308).
- `dna_vocab/v1/` (vocabulary TSVs, alias map, S matrix, adjudications) + `corrections_v1.tsv` (the credit-corrections ledger — travels with the bundle and is applied at every derive, §8 stage 3).
- `manifest.json` (fitted 3-class cut-points per source), `equating_map.json`, `seed_list.json` (the 100-title decade-stratified onboarding list), `judgement_set_v1.tsv`, `audit.json`.

## 5. The model layer (in-app)

### 5.1 Scoring stack (serving)

```
score_u(t) = b(t) + μ_u + w_cf · ⟨v_u, e(t)⟩            e(t) = E[t]      if rated (warm)
                                                        e(t) = gate·E[t] + (1-gate)·ê(t)  else
             b(t) = shrunk item prior; b̂(t) from the Cold Tower for cold titles
             gate = n_t / (n_t + k)                     evidence gating, k≈10
```

**The personal half reads directions (decision 469).** ⟨v_u, e(t)⟩ is taken over d(t): the unit direction of e(t), weighted by the evidence behind it. The weight is its gate when the coordinate is the Backbone's alone and 1 when the Cold Tower contributed to it; a zero row contributes zero. The fit, its cross-validation and both scorers read d(t) through one helper. The reason is scale. The Backbone's rows are support-weighted (E = V·S, so a row's norm grows with its crowd support) and the Cold Tower's ê sits on a third scale, so a raw inner product ranks by popularity and provenance rather than by taste. The coordinates themselves are stored and served unscaled (`title_placement.e_hat`, the blend above, §6.0's model line): the corpus has since answered decision 236's question — E is support-weighted (§4.3, decision 503) — so the artifact stays as shipped, and reading directions is how the personal half meets that scale. Each stored fit records the geometry it was fitted in, and a fit in another geometry is refitted, not served.

Blend with the crowd prior at **β_app = 0.2**. β is the **personal** weight in this codebase, and the corpus project measured the same optimum in the complementary coordinate, so the two numbers are one number under **β_app = 1 − β_corpus**: the corpus's 0.8 and this app's 0.2 (decisions 167 and 234). The "12 → 263 distinct titles" figure — exactly where per-user top-10s stop being the global chart — comes from a corpus table headed "blend beta (1.0 = crowd only)" and is quoted in that coordinate. The app does not *apply* the constant: the nightly fit searches the whole grid per (user, kind) in the orientation it serves in, so what ships is a **ceiling on the personal weight** rather than a served value — `BETA_MAX = 0.8`, a floor of one fifth under the crowd prior, CHECKed in the schema, and a fit that reaches it earned it on held-out accuracy. **Blend, never route** — a learned router was measured to capture 2–3% of the oracle gap and lose to the flat blend. No popularity penalty. Films and series ranked as **separate surfaces**.

### 5.2 The Personal Ledger (the one write-path for taste)

One latent `s_u(t)` per (user, title). Observation arms, all in a single likelihood, refit nightly (full-history MAP; seconds at this scale) and incrementally on each new observation for instant UI feedback:

| Arm | Model | Notes |
|---|---|---|
| 3-class verdicts | ordered logit, free per-user cutpoints | monotone link ⇒ a mis-placed personal threshold widens ties but cannot invert an ordering (measured inversion rate exactly 0.0000) |
| Duels | Davidson Bradley–Terry with ties; **margin-weighted** | tie prior δ from the measured 22% tie rate; margin weighting was selected by tuning, backing the "about the same" button |
| Tier edits (drag-drop, explicit picks) | K-level ordered logit, K = size of the configured tier set (default 7: F/D/C/B/A/A+/S ⇒ 6 learned cutpoints), whose cutpoints **are** the displayed tier boundaries | drag-and-drop = data, not override; the model re-fits around it |
| Rewatch re-ratings | new ordinal observation | drift signal for free |

Fusion math is normative by pointer, and the pointer is **vendored**: `docs/ARCHITECTURE-extracts.md` carries §3 and Appendix C of the corpus project's `ARCHITECTURE.md` (commit `3666eaa`), because a normative sentence nobody in this repository can read is not normative (decision 294). **What is normative here:** the four-arm likelihood of §3 (the equations live there), including its **Davidson-with-ties** form over duels — which is §3's arm 2 and not Appendix C's, whose only comparison model is the ridge anchor plus margin-weighted Bradley-Terry; and from Appendix C, the margin weighting the tuner chose, σ **never as a sample weight** (precision-weighting rows by 1/σ² measured −0.021 — the positive half of that sentence is Appendix C's rank-Gaussian target, which is not what shipped, so there is no σ in this app's likelihood to keep there and `ord_weight` is ones; σ here is the Laplace-diagonal output the badges and the queue read — decision 306), the ridge anchor on the label arm + BT perturbation, and the **ridge-Hessian preconditioner** (fixed-step GD measurably diverges on episodes containing one popular title — this is a scar, keep the preconditioner). **What this section supersedes:** §3's Crowd Head with its per-user low-rank head (R = 16 shared basis deltas) — the app ships no crowd head and no basis deltas, §4.3 carries an artifact for neither, and generalisation is via the 64-d user vector; and §3's random-walk prior on `b_i`, where the shipped model applies a **static ridge** under §4.3's τ. Every constant §4.3 lists comes from `ledger_hyperparams.json`, re-tunable offline in the corpus project. The Ledger's ⟨v, e⟩ reads the same gate-weighted direction d(t) as §5.1's personal half. The fit and the serving path therefore read one coordinate, and one verdict on an off-scale coordinate cannot decide a board (decision 471). The tier arm's cutpoint prior is anchored on the verdict arm's two cutpoints, which sit at the measured shape's 25% and 50% masses, so the three verdict classes and the tier groups F/D/C, B and A/A+/S are one statement about one latent (decision 508). The residual prior τ is 2.0 unless the bundle ships one: a person's own answers on a title outweigh the taste vector there (decision 509). Per-title residuals `b_i^u` capture direct effects. Uncertainty σ per title (Laplace diagonal) drives tier badges ("A/S straddle") and the comparison queue. Freshness: after 12 months untouched, a title's σ inflates Glicko-style at rate c per √month, capped at the prior σ (c and cap from `ledger_hyperparams.json`) — the owner's "keep ratings up to date over time" requirement as ambient recalibration rather than chores.

Display: the 0..1 weight is the **empirical CDF of the user's own fitted `s` values, computed per kind** (their best-ranked title → ~1.0, worst → ~0.0) — the owner's "always-preferred → 1.0, always-rejected → 0.0" definition exactly, and stable under monotone rescaling of `s`.

**Measured expectations to encode in UX copy:** comparisons add resolution *within* the liked class (+0.008..+0.016 at 30 duels, monotone, no cost to global ranking); a decisive pick teaches more than a hesitant one; spreading verdicts across all three classes matters ~5× more than anything the corpus side can tune (a 60%-"liked" labeller gives up ~0.07 ρ) → the rating UI shows a running class balance.

## 6. Surfaces

All surfaces: responsive PWA, phone-first (48 px hit areas, though a control may draw smaller; one-handed, swipe), desktop as progressive enhancement, installable, service-worker shell cache. v1.1's throughput budgets stand: **<2 s per sweep card, <1.5 s per battle**, undo everywhere, next card preloaded. The frame is a phone app's (decision 527): the document scrolls, a translucent tab bar is fixed at the bottom, no root opens on a large title — its top bar names the place or holds its scope switch (Home's kind, Rank's Films/Series, Rate's mode) and each page keeps a visually hidden heading (decision 528) — and its avatar opens **You** (§3.2); the title card, settings and pickers are sheets, a Tonight room's round and reveal and Rank's Place with questions a full-screen flow, and every sheet and pushed view is a history entry that Back closes. On a desktop a sidebar takes the tab bar's place, as a 72 px icon rail between 721 and 1099 px wide and in full from 1100 (decision 528), and a sheet becomes a centred panel.

Surface names (prototype, normative): **Home / Rate / Tonight / Rank / Map / Taste** (+ Admin). A surface whose §12 milestone has not shipped is absent from navigation and from every entry point to it, for both roles — the tab bar, You and the title card's Show on map (§6.0); its route answers by address with a placeholder that says it is not built, in the member register (§6.8), and it enters navigation in this order on the day it ships (decision 488).

**iOS web-push constraint (load-bearing):** on iPhone, Web Push works only for a PWA added to the home screen (iOS 16.4+), and the permission request must run inside a user gesture; iOS has no programmatic install prompt, so member first-run onboarding *guides* Share → Add to Home Screen, detects standalone mode, and **asks for push permission once**, on that phone, honouring a decline rather than re-asking (decision 180). Push is therefore always **best-effort**: every push-carried prompt also exists as an in-app banner, and sessions additionally as a room code/QR.

### 6.1 Rating view

v1.1 §4.3's sweep/battle design survives nearly intact — it was ahead of its time and the measurements vindicated it:

- **Modes:** **Mix** (default — single titles until the person holds 15 live ratings over the session's kinds, then alternates sweep and battle; decision 492), Sweep, Battle; blocks of 15. Members read them as **Mixed**, **Singles** and **Pairs**, chosen with the kinds from the screen title's menu, which names the mode in play and offers "Find a title to rate"; the block counter reads "7 of 15" after the block's fifteen ticks, and a block's end is a screen of its own (decisions 519, 527 and 528).
- **Screen** (decision 528): every Rate screen fits 390x664 and 412x790 with nothing scrolled, its posters keeping 2:3 and shrinking with the height. A single card and a pair share one frame (decision 529): the question in the title face ("How was it?" on a single card, "Which did you enjoy more?" on a pair) with its reason and "Why these?" under it (for 1.6 s after a verdict that line instead echoes the person's answer and the reveal for the film just rated, and after a block's last verdict the end screen, which opens at the reply, carries that echo at its top; decision 530), the film or films with name, year and a **Not seen** pill under each, then the answer row, which starts at the same height and spans the same width on both cards — at the foot of a phone's screen, and on a wider screen right under the films in a left-aligned column whose posters take the window's height up to 420 px, the page no taller than its content; a single card's recall aid takes the second poster's column there. The top bar holds Undo, the mode title, Skip and the avatar, and a disabled Undo has no line under it. A poster never answers: a tap on one, on a pair or a single card, opens **About this film** — the poster, name, year · runtime · genres, the director, three lines of overview, the first four billed cast with their photos (§6.0), and a Not seen button that answers as that side's correction on a pair and as `Not seen` on a single card — which ends on "Looking never counts as an answer." Keys, ignored while typing in a field or while a sheet is open: on a pair ←/→ More, Shift+←/→ Much more, ↓ Same, Q/P Not seen left and right; on a single card 1/2/3 Disliked, Fine and Liked, N Not seen; S Skip and Z Undo on both.
- **Sweep:** one title card → `Liked / Fine / Disliked` (drawn worst to best, as on §6.0's card; decision 517) as three equal tiles, + **`Not seen`** as the pill under the poster (decisions 527 and 529), + `Skip` + persistent Undo (owner decision 2026-08-29: one seen-state control — a title you can't remember is plain `unseen`, §4.2). Verdict implies `seen`, and so does a tier (§6.3, decision 531). Running **class-balance widget**, a small meter of the three counts after the counter that opens **Your mix**, a sheet of the three as labelled bars (decision 528), counting from the first rating, whose warning arms once 15 live ratings stand and one class exceeds 60% (decision 491), with its warning copy in that sheet ("Heavy on '{class}'. Spreading your ratings across all three answers matters about five times more than anything else you can do here. {tail} - but never change an honest answer to even things out."; the tail is "Rate some titles you didn't enjoy as well" for 'liked', "Rate some titles you enjoyed as well" for 'disliked', "When a title was better or worse than fine, say so" for 'fine' — the measured 5× lever) and on the screen as one line, "Heavy on {class} · See why", that opens it (decision 528); before 15 the sheet says "A balance check starts at 15 ratings." Prediction reveal strictly *after* the tap (anchoring; Cosley 2003), phrased "we'd have guessed the same" / "we'd have guessed {class}", its score beside it in the data voice only while the viewer's Show the model (§6.7) is on (decision 486); {class} is the class the title's tier letter stands for, so the reveal and Rank never disagree, and a title nobody has rated wears its guessed class's middle tier, C, B or A (decision 510); a suppressed reveal reads "no guess yet - rate a few more first". The card's "Why these?" disclosure carries the learning-curve copy ("Your suggestions get about three times more personal between 5 and 100 ratings. Aim for 50-100 in your first sitting or two."; decision 527).
- **Battle:** the card asks "Which did you enjoy more?" over two posters and is answered on one row of five, each poster's two on its side: **Much more** records that side's win at the decisive margin weight (~1.6), **More** at the hesitant 1.0, and **Same** a tie (feeds the Davidson tie term), which is never weighted whatever a request sends (decision 528, retiring decision 520's clear-favourite switch and the long-press). Pairs drawn **at random** from the user's seen titles within verdict bands — in a first sitting (fewer than 50 live ratings) from the fine and liked bands only (decision 493) — no clever selection for profiles (measured null; the reason ships as UI copy behind "Why these?": "Pairs are picked at random from titles you rated the same way. For learning your taste, random works as well as anything cleverer. Choosing pairs cleverly only helps when the question is which of a few is best - that is what Sharpen my ranking on Rank and Tonight's round do." — proposal 54a's distinction, restated for members by decisions 491 and 519 with no section numbers on a member surface (decision 486); the card's own why-line is "You rated both {class}", followed by "Why these?" (decisions 519 and 528)). **Not seen** sits under each poster, one tap → sets that side `unseen`, writes no duel row, syncs per §7.3, covered by the persistent Undo; the other title stays on its side and meets a new partner drawn by the same rules, or, where its band has none, a single title takes the pair's place; the API's `both` still sets both aside for a new pair (decision 528).
- **Queue:** P(seen)-ordered (Jellyfin history, popularity, household co-seen, and the person's own answers on titles of the same kind and original language, read against their own seen rate for the kind, which only ever lower it; decision 521), seeded first run from the imported 100-title decade-stratified `seed_list`: every list title leads every other title not recorded seen, and inside the list P(seen) decides, most likely seen first (decision 490). Blocks of 15; each card shows its queue reason as a plain sentence naming its strongest cause ("It's in your library."; a list title "A well-known film from the 1990s." where its crowd support reaches about a thousand ratings, else "A film from the 1990s we ask everyone about first."), with no number in it: P(seen) appears beside it in the data voice only while the viewer's Show the model is on (decisions 486 and 519). Target: 50–100 verdicts in the first sitting or two — every measured curve says the model is still improving at 100 and beyond.
- Onboarding copy sets expectations from the learning curve, counted in ratings: suggestions get about three times more personal between 5 and 100 ratings (decision 491).

### 6.2 Tonight (what to watch now)

**v2.1 redesign (owner decision 2026-08-29), as rewritten by the 54a–54h fold (decisions 175, 214–226):** the visible shortlist stage and the mood-question round are gone, and so is the fixed count. Participants answer this-or-that pairs of real candidates until the shortlist boundary is resolved — **adaptive length**: a median round of about ten pairs at the shipped `boundary_z` on a household's film pool (decision 477), a hard cap of twenty, an escape from the sixth. The answers both decide the evening and carry the mood signal. The measured constraints that survive are marked inline; the round itself is owner-designed, not corpus-measured (§14 risk 6 — instrumented at M4.12, and `session_answer` is the instrument). **Eight steps, numbered stably**, because the coverage map cites them by number: 1 open, 2 join, 3 pool, 4 the round, 5 the shortlist, 6 the ballot, 7 the result, 8 solo.

1. **Initiator opens a session** and picks participants: members and/or N guests. Session controls: kind (film/series), a **runtime budget slider** (soft — the pool admits up to budget + 40 min; a result within budget reads "Fits your time" and one over it "N min over"; on a **series** session the budget is **per episode** — compared with the show's per-episode runtime, never with a season or a series total — and every label that states a number on a series card says so, "15 min over per episode" (decisions 219 and 527)), and a **rewatch toggle** (default: exclude titles *every* participant has seen; "include rewatches" flips it). The door opens on the choice, together or just me, with kind, budget, rewatches and guests as one summary row that opens a sheet (decision 527); the sheet states the budget's softness where it is set ('A little over is fine — we'll say by how much', per episode on a series night), and the slider opens at the budget the member last opened an evening with for that kind on that device, else 130 (decision 506). In the lobby, before Start, each seated member may set up to three **not tonight** vetoes of their own from a fixed list (violence, sexual violence, horror, harrowing), each a set of vocabulary terms, and the pool excludes the union of every member's (decision 505); a title carrying a vetoed term in **either** tier, quote-verified or projected, is not a candidate — a presence predicate that names both tiers and compares no weight (§4.1 rules 1–2) — because a person ruling something out tonight wants recall over precision (decision 504). The vetoes, and whose each is, are frozen with the pool; the lobby shows each member their own and names the others', the open-rooms row shows the union, and a pool they empty is refused naming them (decisions 480 and 505).
2. **Join channels, all equivalent:** push to members' phones (best-effort, §6 preamble); **room code / QR** in the lobby, and the room's **join link** (`/tonight?room=CODE`, the URL a QR would encode), which the lobby shares and the push invitation carries — opening it on a signed-in device joins that room through the same join as every other channel (decision 481); a live in-app lobby banner over the WebSocket; the **open-rooms list** — active sessions are visible to every household device ("MX-2210 · hosted by Mia · 3 min ago · Film · 60 min · skips seen") with tappable empty seats. **Guests use the initiator's phone after the initiator finishes** (hand-the-phone, sequential turns). **Ending a room.** The host, and only the host, may end a live room at any point before it resolves; the room becomes `abandoned`, leaves the open-rooms list, releases its code and refuses every further answer, undo and ballot. Nothing else ends a room that never reaches a result: opening a second room abandons only the host's rooms that nobody has started, and the settle-on-read cures only the case where every seat has already finished (decision 169).
3. **Candidate pool (internal — never shown as a step):** owned titles passing the kind/budget/rewatch filters, ranked by the **plain average** of member Ledger scores (measured: nothing dominates averaging; dominance rules cost −0.012); wherever the evening reads that order — a profile-less guest's prior — the average is taken over each member's scores rank-standardised over the frozen pool (decision 477). Guests contribute no taste term.
4. **The round (adaptive length).** Each participant answers this-or-that pairs of real candidates on their own device — "Which one tonight?" `A` / `B` / `either` / `neither`. *What is being estimated:* per participant, a **tonight score** per candidate — their Ledger score for that title, **rank-standardised over tonight's frozen pool** (the normal quantiles of that member's own ranks at sd 1.0, so every member's stable taste spans the same range and neither member's units can outvote the other's; the rule is named by a scale marker frozen with the pool, so a deploy never moves an evening in flight, and the raw §5.1 scores stay in the snapshot), their stable taste, plus a **mood tilt** learned from this round's answers. The tilt keeps its own units and is not rescaled: on the first household evening it moved a typical title by under a fifth of a pool standard deviation and the titles most like a person's answers by up to about 1.3, while the round's posterior moved the titles those answers named by up to about 2.5 (decision 477). The tilt is chosen-minus-rejected DNA **centred on the candidate-pool mean** (the measured centring lever), and it skips terms the candidate's own vector does not carry rather than centring against a zero it never had (decision 218). A participant with no Ledger — a guest, a member with too few labels — starts from the pool prior and is carried entirely by their answers; a seated *member* with no score row at all is a **named refusal** in the lobby, naming the person, rather than a seat nothing can be asked (decision 216). *How a pair is chosen:* to reduce uncertainty about **which titles belong in the shortlist**, never to rank the pool — among candidates whose posterior interval still straddles the shortlist boundary, the round picks the pair whose answer would most reduce the number still straddling it, ties broken toward the pair spanning the widest DNA axis, because a pair of near-identical titles teaches nothing about the tilt. **One pair in ten** is the uniform-random hold-out (§13) and is chosen by none of this — a **rate drawn from a stable key** rather than a fixed slot, so a round the escape ends at pair six carries hold-outs at the same rate as one that runs to the cap, and one round in eight draws none over a full twenty pairs, which is what a rate means. `session_answer.selection` records it as `adaptive` or `uniform_holdout` and is never accepted from a client. **The draw is sealed for the evening:** the pair a seat is shown at a given answer count is a function of a nonce frozen with the pool, so every read of that card returns the same pair and the same sealed token, and the hold-out stream cannot be made client-selectable by re-reading (decision 223). *Answers:* `A` and `B` separate two candidates; `either` is an equality constraint that lifts both together; `neither` is a rejection that lowers both — the strongest signal a participant can send about a live pool, the most informative answer the selection rule can receive because it eliminates two candidates at once, and the escape from a badly-built pool without abandoning the round (decision 154). Guests' pairs are not seen-filtered (their seen-state is unknown, and under decision 166 there is no stored guest profile that could stand in for it) and are selected to learn **them** — maximising information about the guest's own tilt rather than about a pool the members already discriminate — which naturally makes a guest's round a little longer. *Stopping, per participant:* the round ends when the shortlist boundary is resolved — no candidate's posterior still straddles it within `boundary_z`·σ — subject to a **hard cap of 20 pairs**; from the sixth pair a persistent **"just pick for us"** ends that person's round immediately on what is known so far. Neither the cap nor the escape is a failure state, and both are logged as `session_participant.ended_by` ∈ {`converged`, `cap`, `escape`}: §14 risk 6 wants to know how often each fires. **`boundary_z` is Tonight's own constant and is not §6.3's `straddle_z`.** The two predicates are the same arithmetic over different scales — a Ledger posterior in logit units against learned cutpoints, and a member's score rank-standardised over tonight's pool against the rank-3/4 cut — so one σ multiple cannot calibrate both, and sharing it makes one of them a no-op. Re-measured on the rank-standardised scale over pools of 120, 300 and 700 titles, at z = 1.0 `converged` fires 0–3 times in 20 and the median round is the full cap, so the cap is effectively the only ending there is; `boundary_z` is 0.6, which fires 13–19 in 20 and lands the median round at 9–11 pairs, about ten on a household's film pool — the "about ten quick votes" this redesign was first described in, now an **outcome rather than a quota** (decisions 175, 214 and 477). *Waiting:* participants converge at different points, and someone who finishes early sees the others' **progress and never their answers** — "Patrick 6/6 done · Jenny 12 so far · Mia 4/~10 · waiting for 2"; the ~ figure is an estimate — the typical round, until the seat reaches it — and never the cap (decision 477); past it the line gives the count alone and the seat's own header says the round is running long and names the cap, because a round still running past the typical is the one least likely to end soon (decision 507). All answers stay **hidden until every participant has finished** — the blind-vote social property, preserved by construction. **A pool too small to ask anything is not refused:** admission stays at two candidates or more, and a seat with no pair to serve ends itself with its stop reason, so a pool of two or three settles to the ballot from the next read instead of waiting for ever (decision 215). *Undo:* a retraction is a **tombstone**, never a DELETE — §6's "undo everywhere" reaches the one surface where a mis-tap is otherwise permanent, and §14 risk 6 says log every vote, which a retracted vote still is.
5. **The shortlist.** Per-participant tonight scores are averaged across participants — **plain averaging**, unchanged: no aggregation rule dominates it and dominance rules cost −0.012. The round produces **three finalists and a wildcard**: the top three by group score, plus one exploratory pick honestly labelled ("a step outside your usual" — one exploratory slot in six), drawn from the best twentieth of the ranking (never fewer than twelve candidates) as the one farthest in DNA terms from the finalists — §6.4's prior + proximity (decision 482). Guests contribute answers and no taste term. A hard split — divergent answers on the leading candidates, or Ledger divergence **D ≥ 0.40**, read on the rank-standardised scale (~14.5% of nights as measured on the Ledgers before decision 469, provisional until re-read on the refitted ones; below that, decide silently; decision 478 — the earlier 0.20 was never calibrated, decision 217) — is **surfaced with the alternative in hand** ("You're split on light vs heavy — here's one of each"), never silently averaged. A **facet** split requires the §6.4 axis artifact — a contested facet and an opposite pole to reserve. **The corpus bundle ships no axis artifact** (decision 173; the e2e fixture writes three axis files of its own, which is why the facet branch is testable at all), so with no axis loaded a split is surfaced **by person** instead (decision 479), on D alone — the divergent-answers trigger does not fire it, since decision 217 measured it at 84–97% of evenings. The leader keeps slot 1, and each seat none of whose own top three tonight scores is among the finalists gets one: a plain-top-three finalist that is theirs, or else a slot **reserved for that seat** — its highest tonight-scored title not already placed, slot 3 and then slot 2, still exactly three finalists — recorded as `session_result.reserved_for` and never as the axis counterweight's `reserved`. Copy: "You're pulling different ways tonight — here's one for each of you.", or "You're pulling different ways tonight." when three slots cannot give every seat one of its own. The importer's missing-axes finding is an explicit line on the §10 bundle report, not a log warning. The contested axis is **zeroed, not averaged**, and because zeroing only removes an influence it cannot by itself produce an alternative: **the third finalist slot is reserved for the highest-scoring title on the opposite pole of the contested axis**, and the reveal says so (`session_result.reserved`, decision 220). When no free finalist carries the *reference* pole, slot two is reserved as well — slot 2 to the reference pole, slot 3 to the opposite — so the slate genuinely holds one of each; still exactly three finalists, because this step fixes the count (decision 221). Copy: "You're split on {facet} — here's one of each. The axis is zeroed, not averaged." A member with Show the model off reads the first sentence alone, and D's line without its number (decision 479, in decision 486's register). Conflict copy obeys the measured constraint (DNA_MODEL §5.3): D predicts "one of you is likely to land below your usual tonight" (AUC 0.610), never "someone will hate this" — a hard rule on the §6.6 conflict-phrasing LLM task.
6. **The ballot (blind).** Each participant taps **everything they would be happy with** among the three finalists and the wildcard — an approval ballot, not a ranking. Approvals stay hidden until every participant has submitted; then they are revealed together. The winner is the title with the most approvals, ties broken by group score. **Approval share** — the fraction of participants who approved the winner — is the number §13 evaluates the whole feature on, and `session_ballot` (§4.2) is the only place it exists. A guest seat submits here on the initiator's phone like any other seat: the ballot is keyed by seat rather than by account, and a room holding a seat that cannot submit never reaches the reveal at all.
7. **Result:** winner card — approval share, per-person match lines in DNA terms including the honest negative ("nothing here is their pull — *bleak* works against them"), and **Play on Jellyfin** as the primary CTA — plus runners-up and one **wildcard** ("a step outside your usual, honestly labelled"), with any slot step 5 reserved labelled as reserved — the axis counterweight as the other side of the split, a seat's reserved pick as "{name}'s pick" (decision 479). Votes *choose*; nothing re-ranks within the evening by predicted enjoyment (measured: worth 0.000).
8. **Solo mode** ("Tonight, for {name}"): no session row. It lands **directly on three picks and a wildcard** from the same pool ranked by the personal Ledger with no tilt (rank-standardised over that pool, which leaves the order as it is and puts the sharpen round on the group round's scale; decision 477) — the fastest path to a film must not be slower than browsing Home — each with a one-line why ("{term} · {term}" / "a step outside your usual"), a budget-fit line ("Fits your time" / "21 min over") and Play on Jellyfin (decision 527). A **sharpen this** control runs the same adaptive round against the same pool and re-ranks in place; the provenance line then reads "tilted by your N answers" instead of "unseen first". There is no ballot in solo mode: with one participant, approval share is not a measurement. A **reshuffle** control walks further down the ranking, and says so in one quiet line beside itself when the walk has come back round to where it started (decision 222).

**Guests have no profile** (decision 166). A guest is scored by their session votes alone, every night: no grid, no stored picks, no Ledger, no carry-over from one evening to the next. The measured collapse of pairs-only guest models (§0 row 8) is why a guest is never interviewed *for a profile* — and under this decision there is no profile to interview for, so the 60-title grid that measurement argued for goes out of scope along with the thing it was meant to seed. A guest's votes choose tonight's film and are discarded with the seat.

### 6.3 Rank view (the tier list)

- Per-user table/board of every rated title in tiers **F, D, C, B, A, A+, S** (configurable set; learned cutpoints, not percentile cuts — initialised from DNA_MODEL §4.5's measured quantile shape F 3 / D 7 / C 15 / B 25 / A 25 / A+ 17 / S 8 %, then learned). The shape is realised on the verdict arm's scale: its C/B and B/A cuts sit on the person's own disliked/fine and fine/liked cutpoints (§5.2), so disliked renders in F/D/C, fine in B and liked in A/A+/S; on another tier set the cuts at or nearest the shape's 25% and 50% masses do, so every tier stands for the class the verdict cutpoints give its titles (two tiers, which cannot hold three classes, put disliked and fine in the lower). A rated title stays inside its verdict's tiers, ordered by its fitted `s`, unless the person moved it; where its `s` lies beyond them, its badge names the next tier toward it (decision 508). The board is a tier list (decision 528): the tiers, best first, each headed by its letter, verdict word and count, with its posters in a grid in the board's order — four columns on a phone; on a desktop a band beside its letter cell, at a poster size (small, medium, large) the device remembers. A tier shows two rows until it is opened: its last cell, "+N", opens it in place and fetches the rest, and an open tier offers Show less. On a phone a sticky strip of the tiers' letters and counts jumps to a tier and marks the one in view. Posters load lazily and carry no name beneath, and a tap on one opens its title card. The badge names tier + neighbourhood ("A — between Heat and Prisoners") where the comparison round says where a title now sits (decision 527). A title whose posterior reaches an adjacent tier within `straddle_z`·σ carries the straddle badge "A or S?", drawn on its poster as a small warning dot, and becomes queue-eligible. **One predicate, not two:** the badge and the comparison queue's eligibility are the same test at the same `straddle_z`, so a badged title is exactly a queue-eligible title and the badges are what the queue's entry point counts — two thresholds leave a band of titles queue-eligible and unbadged, which is how that count stops being able to say what the queue will ask (decision 295, proposal 157). The entry point is the **Needs a look** line, the dots' legend: "{n} titles sit between two tiers" with **Sharpen**, or "Sharpen your list" with **Start** while none do; it opens the comparison queue and moves nothing, and no dot is a control of its own (decisions 496 and 528). **At the ends of the scale** the badge names the single adjacent tier that exists — S straddles down to A+, F up to D — and never repeats the title's own tier, which falls out of the arithmetic rather than being clamped afterwards (decision 295, proposal 76). `straddle_z` is a **badge** constant and must be tuned against the σ the fit actually produces: on a real household board the posterior sd (≈1.2) exceeds a tier's width (≈1.1), so z = 1.0 badges ~99% of the board, leaves the 70% boundary arm and the 20% exploration arm drawing from the same set, and makes the chip carry no information. The shipped value is 0.15. Any definition stated as posterior mass is the same predicate re-parameterised and inherits the same problem — at that σ the mass outside a title's own tier is at least 0.65 for every title, so a threshold below that can never exclude anything (decisions 175 and 214).
- **Filters:** genre (decision 473's canonical vocabulary), kind (movie/series — separate by default), decade, runtime, seen-state, DNA facet/term predicates ("show only `mood.cosy`"); all but the kind sit behind one Filters control, as on Home (decision 527).
- **Drag-and-drop rearrange** — the owner's requirement, implemented as Ledger observations: dropping a title into a tier emits a `tier_edit`; dropping it *between* two titles emits that edit **plus two margin-less duels** against its new neighbours. The model refits (incremental immediately, exact nightly); if the model disagrees strongly, the title card's In your ranking row says so ("You put it in {X} — your other answers still point to {Y}") rather than the board snapping back (decision 528) — the user is a data source, not a tyrant, and vice versa. **"Strongly" is the 80% credible interval:** the tension badge fires when the tier the person assigned and the posterior's 80% interval are **disjoint**. A tier is an interval between cutpoints and the posterior is an interval on `s`, so the only coherent reading of "outside" is that the two do not meet; a one-level difference whose bands still overlap is a difference and not a disagreement, and badging those would badge most of a young board (decision 295, proposal 71). **The drag is seen** (decision 528): a mouse drags a poster and a touch screen lifts it by a long press (~400 ms), both through pointer events; the poster lifts (scaled 1.06, a shadow, a 2° tilt) and its cell stays as a ghost; the grid under it opens a slot with an insertion bar and a label naming the spot ("A · between Heat and Prisoners", "top of A", "bottom of A"); the target tier's letter lights and a closed tier opens after 600 ms; the viewport's top and bottom 48 px autoscroll; and on a touch screen a drop on a letter in the tier strip moves the title to that tier, naming no neighbour. A drop's toast, "{name} moved to {tier}", offers Undo when the tier changed, which drops the title back into its old tier naming no neighbour, so no comparison the person never made is written. From the keyboard Space lifts and drops, the arrows move through the grid and past a tier's edge into the next, and Esc cancels, while a polite live region names the spot ("Sicario, lifted. In A, between Heat and Prisoners."); with reduced motion nothing scales, tilts or animates.
- **Without a drag:** the title card (§6.0), wherever it opens (decision 531), carries two rows above the answers: **In your ranking**, with the title's letter and verdict word, which opens an action sheet of the tiers ("Move {name}"), best first with their verdict words, the current one checked, with **Cancel** — choosing a tier drops the title there, the same `tier_edit` semantics, naming no neighbour — and **Place with questions** (below) (decisions 496, 527 and 528). The letter is the person's own: a title not on their board reads "Not placed yet" with no letter, since the tier the model guesses is never shown before the person's own answer (§6.1), and its sheet reads "Rank {name}" with nothing checked; Place with questions shows once the title is on the board and its tier holds another. A tier implies `seen`, and a tier chosen for a title with no live verdict also records, in the drop's own transaction, the verdict that tier stands for (decision 508), so one tap puts a title never rated, or marked not seen, on the board in that tier as seen; that verdict answers no Rate card and carries no reveal, block tick or Rate Undo. The move's toast is the drop's, and its Undo moves the tier alone; a title that had no tier has none to go back to, so its toast, "{name} placed in {tier}", offers no Undo. Off Rank the move replaces no board (decision 531). The sheet is what keeps the move cancellable and legible: one choice from a short list, closed by Cancel, Back or a tap outside, in place of the lift, its banner, the armed rows and the dimming that decision 295 (proposals 74 and 75) asked of a modeless lift.
- **Comparison queue** ("sharpen my ranking"): its pair is answered on §6.1's row without the two Much more steps — More, Same, More, never decisive (decision 201) — and a poster only opens About this film (decision 528). boundary-targeted active selection (70% posterior-straddling pairs / 20% exploration / 10% uniform-random held out for honest evaluation — the adaptive-inflation guard). **Inside the two adaptive arms** (decision 494): neither re-serves a pair already answered; the boundary arm draws its anchor weighted by the height of the cut it straddles and pairs it with the least-compared of the five nearest unasked titles across that cut; exploration breaks least-compared ties toward the higher tier; the titles of the last three answered pairs wait while another can serve. Weighting orders and never removes, and a boundary duel moves titles across a cut, never the cut, which learns from `tier_edit` and the verdict cutpoints it is anchored on (decision 508). The held-out tenth reads none of this and stays uniform and memoryless. ~10–20 comparisons place a new title; a motivated ~500-comparison weekend yields a defensible first cut; the first *stable* tier list arrives at ~1,500–3,000 comparisons (rating-seeded estimate — the unseeded 55%-exact budget is ~3,000 with a measured 1,800–5,800 span controlled by judgement noise σ, unmeasured for these users until §13's re-ask stream runs); ~30–50/week maintains it. **A sitting is a round of 15** (decision 495): the sheet shows the pair as two posters, counts "k of 15 this round" the same way on every arm, ends the round with Done or Keep going, and after each answer names where both titles now sit in the board's own badge words — placement, never "moved", so no answer is singled out; a board whose adaptive pairs are all asked says nothing is left to compare rather than asking for more ratings.
- **Place with questions** (decision 528): one title placed exactly inside its tier by about log2(n) either-or questions (8 in a tier of 150), a binary search over the tier in the board's order. `POST /api/rank/place {title_id, kind}` opens it and returns `{token, left, right, progress: {low, high, size, asked, estimate}}`: the title being placed on the left, the middle of the window still possible on the right. The token is sealed as the comparison queue's pair token is and carries the title, its tier, the window and the count asked; nothing is stored. `POST /api/rank/place/answer {token, outcome: A | B | TIE, decisive}` records a duel through the same observation path as every other, under a context of its own, refits incrementally as the queue does, and narrows the window, returning the next pair or `{done: true, tier, above, below, asked}`; a tie ends the search at that neighbour. `POST /api/rank/place/skip {token}` marks the neighbour not seen, as §6.1's Not seen does, and asks about the adjacent one. The flow is full-screen — "Place {name}" with Cancel back to where it was opened (decision 531) — under a narrowing bar ("Somewhere between #{low} and #{high} of {size} in {tier}", "Question {k} of about {estimate}"), with §6.1's pair and five-step answer and a Not seen pill on the neighbour alone. It ends on "{name} sits in {tier}", "Between {above} and {below} — {k} questions", the neighbourhood's posters with the title ringed as its new spot, **Done**, which also returns there, and **Place another**.
- **Paging** (decision 528): `GET /api/rank` takes an optional `per_tier`, the first N entries of each tier, every tier's count still whole; `GET /api/rank/tier` returns one tier's entries under the same filters by `index`, `offset` and `limit` (at most 200); and a drop answers with the board paged as its client asked. The board is built whole and sliced.

### 6.8 Design language (from the prototype, normative)

Dark-first single-theme UI, warm ("Night cinema", decision 527): ground `#0c0b0a`, surfaces `#1b1916` and `#24211e`, text `#f5f0e8`; one ember accent (`#c8613a` as a fill, `#e58a60` as text) spent on a screen's primary action and on an on state, while choosing one of several is a neutral fill; positive, warning and negative colours always travel with a word or an icon. Poster-forward 2:3 cards, with no tier letter or rank number anywhere but Rank and the title card's In your ranking row (decision 531). TMDB and TVmaze files are re-fetched after 180 days and served `private, max-age=15552000`, never `immutable`. (Decisions 483 and 484, adopting proposal 13 as decision 178 amended it and reversing decision 190.) `title.poster_path` and `title.backdrop_path` hold only a URL on a host this app may serve: the §10 import and §8 stage 3 skip any other when they resolve the card, so IMDb-hosted art (`m.media-amazon.com`) never reaches `title` (decision 501). The member register never renders a spec reference (§N, "decision N", "proposal N") or a milestone label (M0-M7), whether or not Show the model is on; a surface that is not built says so and that it is coming in a later update. Model numbers - b(t), β, σ/±, gate, s, cdf, cos, D, cutpoints, straddle, support n, salience, confidence, held-out rates - and the model's own nouns - prior, fold-in, posterior, ledger (as the model), Backbone, Cold Tower, bundle and its version, e_source, tier_edit, duel, observation, refit, and "labels" as a count of verdicts - reach a member only while that member's Show the model is on, in the data voice next to their name. ## 7. Jellyfin integration

### 7.1 Connector

Ported auth + field list from the corpus connector (`X-Emby-Token`, `/Users`, `/Users/{id}/Items` with the proven FIELDS set incl. ProviderIds, MediaStreams, DateCreated, UserData). Pin Jellyfin ≥ 10.9; new read code prefers the modern `/Items?userId=` route (the corpus connector's `/Users/{id}/Items` is the legacy alias). Identity: ProviderIds → `imdb/tmdb/tvdb` + `jellyfin_id`; upsert into `title` by the ported fill-never-clobber resolver. **Play on Jellyfin** (title card, Tonight winner): deep-link to the server's web player (`{jf_url}/web/#/details?id={jellyfin_id}`); direct playback is a later refinement.

### 7.2 New-title trigger (owner requirement: every Jellyfin add triggers acquisition)

- **Primary:** the Jellyfin **Webhook plugin** → `POST /events/jellyfin` (`ItemAdded`), token-authed. Debounce 10 min (library scans add seasons in bursts; series acquire per-show, not per-episode).
- **Fallback:** 15-minute delta poll on what the server saved since the last poll (`MinDateLastSaved`, read back from a watermark written five minutes behind the poll's start) and not on `DateCreated > last_sync` — Jellyfin stamps `DateCreated` from the file or an NFO, so it says nothing about when an item entered the library (decision 409). The corpus connector is full-mirror only — the delta path is new code, flagged as such.
- Both paths enqueue an **acquisition job** (§8) per new title, and neither writes ownership. Only the full sweep may mark removed titles `is_owned = false` — the complete read of the library the admin key can see, made on §7.3's fifteen-minute sync, which un-owns nothing after a read it could not finish — because a delta poll is an add detector that can never observe an absence and one `ItemAdded` says nothing about what the library no longer holds (flag re-derived from Jellyfin, never trusted stale — the corpus flag is equivalent to `jellyfin_id IS NOT NULL` today but goes stale the moment the library changes). (Decision 362.)

### 7.3 Seen-state sync (two-way; new relative to the corpus project's read-only stance)

- **App is authoritative for explicit user actions.** `seen`/`unseen` set in the app writes Jellyfin's per-user Played flag via `POST/DELETE /UserPlayedItems/{itemId}?userId=` (the ≥10.9 route). **Jellyfin API keys are unscoped and admin-equivalent — no read-only variant exists** — so the setup copy says exactly that ("the Jellyfin API key grants full server access; this app uses it for reads and per-user Played writes only") and write restraint is enforced by this app's code alone. Preferred least-privilege write path: at user-link time obtain per-user access tokens (`POST /Users/AuthenticateByName`) for the linked users, store them in `connector_config`, and use each user's own token for their Played writes (a user token can only set its own state); the admin key stays read-only-by-policy for library/user enumeration. Costs: one-time password entry per linked user; a 401 on write → re-link prompt. The mapping is the plain boolean: `seen` → Played = true, `unseen` → Played = false (v2.1 — the `forgotten` state is gone). **Series are asymmetric.** For `kind = 'series'`, `seen` still writes Played = true on the Series item, but `unseen` is app-only and is never written: Jellyfin executes `DELETE /UserPlayedItems/{seriesId}` as a recursive `MarkUnplayed` that zeroes `PlaybackPositionTicks`, `PlayCount` and `LastPlayedDate` on every episode — history this app never owned and cannot restore. The row is stamped `jf_synced_at` so the sweep does not re-owe the write, and the surface says the change is app-only. (Decision 210.)
- **Jellyfin playback is a suggestion, never a silent write:** ≥90% playback (poll `/Sessions` + `IsPlayed` delta) arms a per-user prompt — "Did you finish X?" → one tap sets `seen` and offers the verdict flow (v1.1 §4.1 capture, kept). Push notification if the user isn't in the app — best-effort (§6 preamble); when undeliverable, the prompt queues and surfaces as an in-app banner on next open. The banner path is the whole M1 behaviour; push arrives with the M4 stack. **A sweep never answers the question it asked.** While a finish prompt for a (user, title) is open, the 15-minute seen sync leaves that row alone; only a tap closes it — `yes` writes `seen`, `no` writes `unseen`, both as explicit user actions under the conflict rule below. (Decision 211.)
- Conflict rule: last-writer-wins with the app's explicit action outranking Jellyfin's inferred state; `jf_synced_at` prevents loops. A **series** Played flag is computed by Jellyfin from its episodes (`played >= total`, and `true` for an empty folder) rather than asserted by a person, so it never overrides an app-side row in either direction: Jellyfin played over an *absent* row is adopted, because an absent row is a default and Jellyfin's history is real history; Jellyfin not-played over an app `seen` is ignored, because a show does not become less watched when a new season lands; and Jellyfin played over an app `unseen` is ignored too, because `unseen` on a series is app-only by decision 210(a) — the app never sent it, so the folder's disagreement is the design and not news. (Decisions 210 and 213.)
- **External playback events** (v1.1 §6.1, kept verbatim): `POST /events/playback` token-authed, for the theater path that bypasses Jellyfin — the designated Home Assistant seam (§11). **It is not built, and it is not part of §12's M1 row:** `playback_event.source = 'external'` exists in the schema (`0005_ledger.sql`) and no router serves the route, so §13's rating-capture input for a film watched outside Jellyfin has no producer. **M7 owes it**, with §11's other two seams (decision 290).

## 8. New-title acquisition workflow

Ported skeleton: the corpus project's raw store (content-addressed, immutable — crawl once, re-parse forever), durable `(kind,key)` queue, per-host rate-limited HTTP layer, and the single-title prototype (`mdc probe`). New code: per-title incremental derive (the corpus `rebuild`/`project`/`ingest` are deliberately wholesale).

**Pipeline per title** (stages visible in the admin board):

```
1  identify      Jellyfin ProviderIds → title row (fill-never-clobber); a row is
                 MINTED only on a provider id (imdb/tmdb/tvdb) — an item Jellyfin
                 supplies no provider id for parks here with the reason "no provider
                 id" and mints nothing, because a name-and-year mint is the wrong
                 match the resolver already refuses (decision 323)
2  enrich        tmdb:resolve → tmdb:detail (metadata, credits, keywords)
                 wikidata:resolve (→ MC/RT/Letterboxd slugs — halves guessing)

3  derive        per-title parse of raw docs → title_meta/credit/review/…
                 (single-title version of the corpus rebuild, keyed entity_key);
                 ends by applying BOTH curated ledgers — adjudications_v1.tsv
                 and corrections_v1.tsv — exactly as the corpus rebuild runs
                 corrections last: a derive that regenerates rows without
                 re-applying them silently reverts curated fixes (§14.5)
4  reviews gate  pack requires plot + multi-source reviews ≥50 words; if thin,
                 retry window 30 days (new releases accrue reviews over weeks)
5  dna pack      ported packs.py (interleaving, caps, norm()) + craft supplement
                 (wikipedia craft sections; NOTE: the RT critic-blurb pool is a
                 frozen 2020 dataset → genuinely new releases get thinner
                 sound/visual facets — known gap, mitigation: wiki sections +
                 metacritic critic excerpts, revisit if coverage measures poor)
                 a Wikipedia or MPST plot another title also carries is left
                 out of the pack (decision 499)
6  dna extract   LLM structured call(s) against the frozen vocabulary —
                 1..N providers per admin config; two passes recommended
                 (union +13pp recall); ~20–27k input tokens/pass/title
7  verify        ported trust boundary verbatim: term-in-vocabulary (after
                 alias repair + adjudication rename), quote-substring-of-pack
                 via norm(), salience ∈ {1,2,3}. 100% catch rate on fabricated
                 tags in the corpus pilot. Failures drop, never repaired. The
                 verdict is reached inside stage 6, whose one retry must name
                 the violation to a call that has not yet returned (decision
                 432); this stage records it - the tags stage 6 stored and the
                 rejects its run filed - and verifies nothing a second time
                 (decision 462)
8  project       per-title alias-map projection of its keywords (incremental —
                 new code, same alias map) for an acquired title; a bundle
                 title's projected rows are seeded once (decision 162), and
                 this stage leaves them alone (decision 463); an alias row of
                 kind `lexicon` never projects, and the loader stores `kind`
```

Failure at any stage parks the job with a reason, retryable from admin; paid stages (6) never auto-retry past the spend cap. All fetched bytes land in the app's own raw store, so re-parsing is free forever.

**A bundle title the corpus never fetched TMDB for (decision 522).** Stage 1's exit for a bundle title the app has already placed (decision 411) stands for the pipeline. A bundle title, placed or not, that has no TMDB block in `title_meta` is walked by the worker's `metadata-backfill` job, through stage 2's `tmdb:resolve -> tmdb:detail` and stage 3's derive and nothing else: no other source, no paid stage, no placement and no board row. Titles the household owns come first, then titles a member has seen or rated, then the seed list, then placed titles and then the rest, up to 100 a half hour through the same polite fetcher. The card's text and poster arrive through stage 3's card resolution. A field is replaced only by the value of the source that leads the corpus's order, and year, runtime and language are never overwritten. This derive does not apply the adjudication ledger, so the extracted DNA tier stays as the bundle seeded it; the corrections ledger still runs last. An id the walk filled that another title already carries is set back to empty. TMDB holding no record is asked again after 30 days, a refused key stops the run, and with no key nothing is walked.

**The fetcher is polite, and says so in a form that can be failed (decision 340).** It declares a User-Agent naming the app; it honours each host's `robots.txt`, fetched per host and cached in Postgres; and it carries per-host rate and concurrency policies as data rather than as constants. An override of a host's robots.txt is permitted only where it is documented with its reasoning beside the policy it changes. The household's own Jellyfin server is exempt: it is reached with the household's own key and is not a third party to be polite to. The backend process holds one such fetcher for its lifetime, for the two image hosts §6.8 serves art from and no other, since no other process reaches them; each host has a declared row (decision 485).

### 8.4 The extraction flywheel

A queue of *naming failures* that future LLM spend should fix, fed automatically: compositional queries hitting empty predicates, explore frontiers with no vocabulary coverage, thin-facet titles. The fourth feed earlier drafts listed, titles whose "unnamed taste" residual share is high, is struck: nothing this repository can read defines the measure (decision 328). Admin reviews the queue, picks a batch and providers, sees the cost estimate, launches. The pass count is chosen per batch with the providers; the estimate is shown as the batch's reservation of both attempts against what remains of the monthly cap; and Launch is refused with its reason, never warned after the fact, when that reservation exceeds what remains, when no cap is set, when the batch's plan cannot be made or when a price is unknown (decision 441). This is how DNA breadth grows *where it's needed* — breadth being the measured binding constraint (zero owned titles carry `themes.robots`). **The enqueue is immediate and visible:** a failure is in the admin queue from the moment it is observed, with its reason and a "queued just now" marker read off the row's own creation time — a live instrument, never a nightly digest. A title is **thin-facet** when at least one facet the active vocabulary declares carries no extracted-tier term for it — every declared facet must be named, eleven on vocabulary v1, and no count threshold applies — and its row is written the moment its walk finishes stage 8; this is a different test from the per-block `is_thin` placement uses (§4.1). The first two feeds are produced by §6.4's compositional search and explore frontier, which are M6's, so at M5 the thin-facet title is the one feed with a producer. A failure naming a term the vocabulary does not carry is not enqueued, because no batch can add one (decisions 163, 328, 329, 330, 344, 440).

Total ≈ **1.15 GB** uncompressed (~0.35 GB compressed). Importer enforces every §4.1 landmine rule and produces a migration report (counts per table, validation failures, vocabulary version). **Model re-import (retrained backbone) is a planned admin event with a migration report** — never a silent sync, and never a diff report, which does not exist. **Content seeds once** (decision 162): the re-import that arrives carries models, not content. **A vocabulary change is refused until a migration plan exists** (decision 163, §14 risk 7). Ledger *observations* always survive re-import (they reference `title.id` and vocabulary-independent facts) — but the rebuild set is larger than the DNA caches: **everything expressed in the old Backbone's basis is garbage against a new one**. Re-import therefore recomputes: user fold-in vectors (closed-form, ms), per-label-count blend weights, a full Ledger MAP refit, Cold Tower re-placement of every app-acquired title (feature vectors rebuilt from the staged bundle's feature contract, whose column set may change). (The v1 Map is a deterministic axis scatter and needs no rebuild — a future UMAP lens would recompute here.) Swap sequence: validate → stage to `/data/artifacts/<version>/` → recompute the rebuild set against the staged bundle → transactionally flip `artifact_bundle.active`. The sequence ends at the flip: the backend loads the flipped bundle within seconds (it re-reads the active row on a timer and before it answers Movie data, and replaces store, Backbone and constants together), and the worker reads it on its next job. This holds for a first import, a models-only re-import and a restage alike. A restart of backend + worker is owed only when that load fails, and Movie data, the wizard and the header then say so and name the command (decision 497). Invariant: no process may score or refit with a loaded bundle version different from the active row.

**The bundle is private household data.** It is assembled under personal and non-commercial terms — verbatim MovieLens tables, scraped IMDb reviews and IMDb-derived tables, Metacritic and Trakt bodies whose own `rating_source` rows read "not redistributed", whole critic articles, MPST synopses, OMDb CC BY-NC text and TMDB content — so it is **never published with a release, never shipped as a release asset and never handed to another household**. The `/data/backups` movie-data archive inherits the same restriction, and `LICENSE` (MIT) covers this repository's code and nothing in the bundle. The per-source terms the app has to display travel with the data, in `rating_source`'s `url` / `license` / `version` / `notes`, and the surface that reads those four columns out today is §6.6's admin **Data** card. /account's **Data sources** block carries this app's own notices — IMDb's courtesy line, TMDB's "not endorsed, certified, or otherwise approved by TMDB", CC BY-SA credit for Wikipedia and TVmaze, OMDb's CC BY-NC — in §6.8's quiet data voice, one notice on one surface and never a source name on every card (decisions 292 and 293). **A member-readable route for the per-source terms is not built** (decision 307): the one route serving those columns takes `AdminUser`, so a household's non-admin member cannot reach the eleven datasets' own licence text, and this file records that as an unmet promise rather than implying it is kept.

**Corpus-project deliverable to build:** `mdc export-bundle` implementing this manifest — deny-listing `%_bak%`/`%_good`, live tables only, `content.npz` slimmed by dropping the per-user affinity arrays (`aff` + `aff_den`, ~1.29 GB) while keeping the item stats (incl. `item_n`), filtered `imdb_ratings`/`ml_link` joins, both curated ledgers, the feature contract with its frozen `text_scale`, and the tuned ledger hyperparameters persisted to `ledger_hyperparams.json` (today the tuner only prints them).

## 13. Evaluation

Surviving v1.1 §8 rows, inlined with their targets: pick-through > 60%; post-watch quality ≥ manual picking; rating capture > 70% of finished playbacks; winner approval share (target: the winner appears in a majority of every participant's favourable votes); satisfaction spread < 0.3; diversity drift — no sustained narrowing. Dropped rows: profile coverage over n_u, ledger drift over deficit_i, session length ≤ 10 (all tied to the deleted 8-axis/fairness machinery; the round's length is adaptive and capped at 20 by design, §6.2 step 4). Added: per-user held-out Spearman vs the crowd-derived expectation curves (§0 row 1's numbers are the M2 yardstick); within-liked resolution as duels accrue; not-seen rate in the rating queue (>50% = queue bug); cold-title badge accuracy once new titles get rated; DNA coverage of naming events (queries answered vs sent to flywheel); **shortlist stability** — how often Tonight's held-out pairs agree with the adaptive shortlist; and the **rate at which the round's cap and escape fire** (`session_participant.ended_by`, §14 risk 6).

Two mandated data streams from day one: (a) the 10% uniform-random comparison stream is the *only* data used to evaluate the tier model — adaptively-selected pairs inflate reliability (measured effect; the guard is non-negotiable), **and since §6.2's round became adaptive with a data-dependent stopping rule the same guard binds Tonight**: `session_answer.selection = 'uniform_holdout'` is drawn as a rate from a key sealed with the pool, is used for neither selection nor stopping, and is the only data admissible for evaluating the round (decision 223); (b) a separate silent **re-ask stream** — ~10% of comparisons/verdicts re-asked after ≥3 days; ~200 re-asks measure the flip rate σ that sets the tier budget (DNA_MODEL §4.2 build-order #1) and settles the corpus's zero-test-retest-data unknown. The two streams are different instruments: the uniform-random stream cannot measure test–retest consistency.

## 14. Risks

1. **Two-person reality vs crowd proxies** — every number is a crowd measurement; M2 is the test. Mitigation: expectations instrumented, not assumed.
2. **New-release DNA thinness** (craft-blurb gap, review-accrual lag) — mitigations in §8 stage 4/5; measure facet coverage of post-2025 titles.
3. **Jellyfin credential custody** — API keys are unscoped and admin-equivalent (no read-only variant exists), so the stored connector secret can administer the whole media server; write restraint is app-side policy only. This raises the stakes on §2's secrets encryption, and is why §7.3 prefers per-user tokens for the write path.
4. **WebAuthn origin coupling** — `PUBLIC_URL` change invalidates passkeys; wizard warns loudly.
5. **Per-title incremental derive is new code** replacing deliberately-wholesale corpus steps — port the invariants (raw/derived split, idempotent re-ingest, adjudication- **and corrections-**at-derivation — two distinct ledgers: DNA verdicts at ingest, source-credit facts at rebuild) or inherit the bugs they were built to kill (the 787-rows-reverted-twice scar).
6. **The vote round is unmeasured** — the adaptive round of §6.2 step 4 (v2.1's owner decision as rewritten by the 54a–54h fold) replaces the corpus-measured shortlist + question instrument. The surviving measured constraints are encoded in §6.2. **The instrument now exists and the comparison has not been made:** M4.12 made every answer loggable with its real latency, its `selection` arm and each seat's `ended_by`, so the rate at which the cap and the escape fire is readable (§4.2, §13) — but winner satisfaction has still never been compared against the solo baseline on a household's own evenings, and nobody tunes `boundary_z`, the cap or the escape until it has.
7. **Vocabulary evolution across the project boundary** — a vocabulary change is a **migration, not an import**. Under decision 162 a re-import carries models, not content, so a models-only bundle shipping `dna_vocab/v2` would leave `dna_tag` and `dna_projected` at v1 while the feature builder filters on the active version, and **both DNA blocks would go empty for every title** — a silent catastrophe rather than an error, and unrecoverable for the extracted tier, whose 2,016 quote-verified titles no re-projection reproduces. Until a migration plan exists the importer **refuses** a vocabulary version change and says why (decision 163), so no import this build performs can introduce a second one. Two vocabularies in the tables is a state this build does not create and must still survive — the way in is the migration decision 163 defers, which §8.4's naming-failure queue is what will eventually ask for — so **every read is scoped to one version**: a tilt, a conflict explanation or a DNA card computed over a superseded vocabulary is the app reasoning in a basis that is not the active row's (v1.1 §10.3-5 stands).
